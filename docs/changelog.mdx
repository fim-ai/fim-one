## [Unreleased]

### Added

- **Sign-ins through GitHub, Google, Discord or Feishu appear in the sign-in history, and every sign-in says how it was made.** A sign-in through an OAuth provider left no record: Settings → Security and Admin → Security → Login History showed password and email-code sign-ins only. Provider sign-ins are now recorded with the caller's IP address and browser, including one refused because registration is closed. Each sign-in record carries its method (`password`, `email_code` or `oauth:<provider>`), returned as `method` by `GET /api/me/sessions` and `GET /api/admin/login-history`; the two-factor step repeats the method of the sign-in it completes. An account created by a first provider sign-in is recorded in the audit log.
- **Account security actions are recorded in the audit log.** Registering, the first-time administrator setup, changing or setting a password, resetting one by emailed code, switching two-factor authentication on or off, generating new backup codes, linking or unlinking a sign-in provider, creating, enabling, disabling or deleting one of your own API keys, and signing out of all sessions each leave an audit entry naming the user and the IP address and browser the request came from. No entry holds a password, a code, a two-factor secret or a key (an API key is named by its id and display prefix). The entries are listed in Admin → Audit Log.
- **Audit log entries say where the request came from and how it ended.** An entry in Admin → Audit Log held the operator, the action, the target and a line of text. New entries also record the client IP address and browser, whether the actor is a platform administrator, a user or the system, how they were signed in (session or API key; a key is named by its id, never its value), the organization the affected thing belongs to, and the outcome (success, denied or failed). The audit list API and the CSV export carry the new fields. Entries written before this release leave them empty and read as an administrator's successful action. An operator name longer than 50 characters (a long email address) no longer makes the entry fail to save on PostgreSQL.
- **A workflow run that waits for an approval survives a restart, and no longer has to stay in the server process.** A Human Intervention step used to wait inside the process that ran the workflow: a restart or deployment lost the wait and the run with it, and the approval stayed open with nothing behind it. The run is now stored as `waiting` at the step, with its variables and what each step has produced, and is continued once the request is decided: after the step when approved, as a failed step when rejected or when the request's time runs out. It is continued by whichever server process hears of the decision, exactly once however many processes or screens act at the same moment, and a decision made while the service was down is picked up when it starts. Time spent waiting does not count toward the run's time limit, and a waiting run holds none of your concurrent-run slots. When it is continued it is checked like a run starting then (your account, quota and plan, the owner's account, the workflow still switched on for trigger and schedule runs) and fails with that refusal if it would be refused; it then takes a concurrent-run slot, queueing for one if none is free (shown as queued, ahead of your new runs, for at most an hour: `WORKFLOW_RESUME_SLOT_WAIT_SECONDS`). One user can have 20 runs waiting at a time (`WORKFLOW_MAX_WAITING_RUNS_PER_USER`); at the limit, a workflow with a step that waits is refused before it starts with `workflow_waiting_limit_reached` (a batch starts only as many items as may still wait and reports the rest as not started), and runs that reach their approvals at the same moment cannot exceed it. What a waiting run keeps (its variables and step outputs) is stored encrypted, and a run that would have to keep more than 5 MB (`WORKFLOW_SUSPEND_STATE_MAX_BYTES`) fails at the step with `workflow_suspend_state_too_large`. A rejected or unanswered approval is final for the step: its retries do not ask again. A trigger-key call that reaches an approval now answers at once with `"status": "waiting"` and the run id instead of holding the connection.
- **An approval inbox.** Workflows → Approvals lists what you are being asked to decide: approval steps assigned to you or on your own runs, and confirmations of connector actions on your runs. Each entry names the workflow and the step, who started the run, when the request runs out, and the step's message or the action and arguments about to be sent. Approve or reject there, with an optional note; a badge on the Workflows page counts what is waiting. If someone decided first on another screen or in a channel, the entry says how it was decided instead of failing. The run panel shows the same state while you have the workflow open.
- **A connector action that requires confirmation can be used in a workflow.** A Connector step whose action is flagged "requires confirmation" used to fail. It now asks: the run waits, the person the run belongs to confirms in the approval inbox (for a trigger key or a schedule, the workflow's owner; administrators may always decide), and the action runs once confirmed. What is confirmed is what runs: the arguments shown in the request are the ones sent, whatever variables changed while it waited, and if the action, its connector, or whose credential the call would use changed in the meantime nothing is sent and the step fails. The arguments are stored encrypted; values that come from the workflow's env vars are shown as `{{env.NAME}}`, and long arguments have to be opened before Approve is available. Rejected, or unanswered for 24 hours, the step fails and says which. A single-step test and a workflow that an agent runs as a tool cannot wait for a person, so there the step still fails.
- **The Start step can check a run's inputs before anything runs.** With "Check inputs before a run starts" on, every way of starting the workflow (the Run button, a batch, a trigger key, a schedule, an agent's `run_workflow`) checks the inputs against the Start step's list first: a missing required input is refused with `workflow_input_required`, one of the wrong type with `workflow_input_invalid`, both naming the input (a batch names the row too). Inputs reach the steps in their declared type: Text, Number, Boolean, JSON or List, so `"5"` sent for a Number arrives as the number 5. A number given as text must be written plainly (`12`, `-0.5`, `1e3`). An optional input left empty is not passed on, except that empty text for a Text input is passed as empty text. The switch is on for new workflows; existing workflows keep receiving their inputs exactly as sent until you turn it on.
- **A workflow MCP Tool step can be given the tool's arguments in the editor.** The step had a field for the tool's name and none for its arguments, so a tool that needs any could only be used by editing an exported workflow file. After you choose a server, the editor asks it for its tools: the tool is picked from a dropdown, and each argument the tool describes gets a field of its own, with the description, a mark on required ones, a dropdown for a fixed set of values, and "Insert variable" for `{{variable}}` references. "Edit as JSON" shows the same arguments as one JSON object, and is what you get for a tool that does not describe its arguments. A number typed as `1.0`, `.5`, `1e3` or `007` is stored as a number once you leave the field, and text in a number field that is neither a number nor a `{{variable}}` is marked in the field. Text in the JSON editor that is not a JSON object yet is not stored in the step (the step keeps its last valid arguments, and the editor says so); it stays in the editor when you select another step and come back, for as long as the page is open. If the server cannot be reached, the reason is shown with a Retry button, and the tool's name and JSON arguments can still be typed. The server is opened with the credential a step run by you would use, so a server you could not call in a run cannot be listed either. At run time, a `{{variable}}` filled into an argument the tool declares as a number, a boolean, an object or a list is passed in that type; it used to arrive as text, which servers that validate their input reject. An object or list argument is read as JSON before its references are filled in, so a value lands in one place of the structure (as a string, a number or a sub-tree) and cannot add keys or items beside itself; a reference written without quotes (`{"count": {{n}}}`) whose value is text is read as the JSON that text is (`5` is the number 5, `true` a boolean, `null` null, `{"k": [1]}` that object) and stays a string when it is not JSON (or is a number too large to be one, such as `1e999`), while a quoted reference (`"{{n}}"`) is always a string; a filled-in value is never read as a template again. References inside the objects and lists of arguments entered as JSON are filled in at any depth (they used to be passed on as the literal `{{…}}` text), and the same holds for the parameters of a Connector step. Where the result is text (a Connector step's parameter, an argument the tool does not describe) and the template itself is a JSON object or list, each reference is replaced where it stands by JSON of its value (the rest of the text, its numbers, key order and spacing, is left exactly as written), so a value cannot add keys to JSON that the receiving side goes on to parse. For an integer the filled-in text may be written `3`, `3.0` or `3e2`; text that is not a plain number (`1_000`, `nan`, non-ASCII digits) is passed as text for the tool to judge, and so is any argument whose declared types include text.
- **A workflow Connector step can query a database connector.** A Connector step that named a database connector failed with "Action not found", for the connector's owner too. The step now runs one of the three operations a chat with the connector gets: list its tables, describe one table, or run a SQL query. A `{{variable}}` in the table name is filled in before the step runs; a `{{variable}}` in the SQL is sent to the database as a bound value, separately from the SQL text, so whatever the value holds (quotes, comment markers, SQL keywords) it is compared or stored as that value and cannot change the query. Numbers, booleans and empty values keep their type on PostgreSQL and DM8 (on MySQL every value is sent as text, see Security below); a list that is all there is inside `IN ({{ids}})` is bound as one value per item (an empty list is an empty set: `IN` is false for every row and `NOT IN` true), and anywhere else a list or an object is sent as JSON text (on PostgreSQL a list also fits an array, as in `= ANY({{ids}})`). PostgreSQL takes at most 32767 bound values in one statement: a longer list in `IN (…)` fails the step with a message that says to write `= ANY({{ids}})`, which binds the whole list as one value. A number with a fraction bound where PostgreSQL expects an integer fails the step instead of being cut down to the integer. It uses the same tool chat does: the connector's read-only switch, row limit and timeout apply, columns marked as personal data come back masked, and each call is written to the call log with the workflow run it belongs to. As in chat, only the connector's owner can use it: when anyone else runs the workflow, the step fails with "can only be used by its owner", whatever the connector's fallback switch says. A query the connector refuses or that fails (a write on a read-only connector, a timeout, a SQL error) fails the step with the database's message. A `{{variable}}` can therefore stand only where SQL takes a value, written without quotes (`WHERE id = {{start_1.order_id}}`): inside a quoted string, a quoted name or a comment, or in place of a table name, a column name, a keyword or the whole statement, the step fails before anything runs and says how to write it. For a pattern, join the pieces in SQL (`LIKE '%' || {{start_1.q}} || '%'`, or `CONCAT('%', {{start_1.q}}, '%')` on MySQL). A variable that has no value in the run fails the step. Bound values are supported for every database type the connector offers (PostgreSQL, KingbaseES, HighGo, MySQL and DM8). In the editor, the step's connector dropdown now lists your own database connectors; choosing one replaces the action and parameter fields with an Operation dropdown, a table name field for "Describe a table" and a SQL field for "Run a SQL query".
- **MCP tool calls are recorded in the call log.** A call to an MCP server left no record, whether it was made from chat or by a workflow MCP step. Each call now writes a call-log entry like a connector call does: who made it, the server and the tool, when, how long it took and whether it succeeded. Admin → Connectors and Admin → Analytics → By Connector count these calls and show an MCP server as "name (MCP)". The "calls today" figure on your own dashboard still counts connector calls only. Calls to the instance-wide servers configured through `MCP_SERVERS` are not recorded. The error text stored with a failed call no longer keeps the user name, password or query string of a URL it quotes.
- **A call record says where the call came from and whose credential it used.** Connector, database and MCP call records now note the entry point (chat with an agent, chat without one, a delegated agent, a workflow step), the workflow run for a call made by a workflow, and whether the call went out with the caller's own credential, the owner's, the owner's borrowed through fallback, or none. A call made by an agent you delegated to with `call_agent` is recorded under that agent; it used to be recorded with no agent.
- **Organizations can add Lark, Slack and WeCom webhooks and email lists as channels.** Settings → Channels offered one type, the Feishu app. An org admin can now also create a Lark / Feishu, Slack or WeCom group-bot webhook channel, or an email channel with a fixed list of recipients, and use it for an agent's completion notification. A webhook URL must be on the platform's own host and is stored encrypted and never shown again; an email channel sends from the instance SMTP account and only to recipients the operator's allowlist permits. These types send only: an approval channel still has to be a Feishu app, and the agent editor lists only those for approvals. The unused `wecom` and `slack` type names, which could be saved through the API but never delivered anything, are no longer accepted.

### Changed

- **Behavior change: invite codes are no longer written to the audit log in full.** Creating an invite code wrote the whole code into the audit entry, and the audit CSV export carried it out. The entry now shows the first four characters, enough to tell which code it was, and names the code by its id; revoking a code is recorded the same way. Entries written before this release are not rewritten. A URL quoted in an audit entry's detail text is stored without its user name, password, query string and token-shaped path segments.
- **Behavior change: a schedule skips its time while its previous run has not ended.** A scheduled workflow started a new run at every scheduled time, also while the previous scheduled run was still running or waiting for an approval, so runs piled up. The scheduled time is now skipped (not made up for later) until that run ends; the schedule dialog says so while it applies. Runs started by hand or by a trigger key do not hold the schedule.
- **Behavior change: closing the tab no longer cancels a workflow run.** A run started with the Run button was cancelled when the browser tab closed or the connection dropped. It now runs to its end regardless; reopening the workflow or its Run History shows where it is, with each step's result appearing as the step finishes. Use Stop to cancel a run. Stop now also works for a run that is waiting for an approval and for a run being executed by another server process: there, no further step is started, while a step already in progress runs to its end or is stopped within about 10 seconds. API change: `POST /api/workflows/{id}/runs/{run_id}/cancel` on a run that has already ended answers 409 `workflow_run_already_finished` (with the run's status) instead of 200 `cancelled: true`.
- **Behavior change: a workflow run interrupted by a restart is closed as failed.** A run that was executing when the server stopped stayed `running` forever, and for a workflow with a trigger key every later call was refused with `workflow_already_running`. Each server process now marks the runs it is executing every few seconds, from a thread of its own so that a long blocking step cannot stop it, and by the database's clock; a run whose mark has gone stale (90 seconds by default) is closed as failed with "The server stopped while this run was in progress", its open approval requests are closed, the owner's run-failed webhook is sent, and the trigger key works again. Upgrade note: runs that were already `running` when this version is first started carry no mark. With a stop-then-start deployment nothing is executing them and they are closed 30 minutes after the new process starts (`WORKFLOW_RUN_LEGACY_GRACE_SECONDS`); with a rolling deployment that same wait gives the old process time to finish the runs it is still executing. Working directories left behind by such runs are removed.
- **A run that ends closes its approval requests.** Cancelling a run, or a run failing or timing out while one of its steps waited for a decision, left the request open in the approver's list with nothing to approve. The request is now closed with the run.
- **A cancelled workflow run is recorded as cancelled.** Depending on which step was running, a stopped run could be recorded as completed or failed.
- **The workflow approval endpoints are replaced.** `GET /api/workflows/approvals/pending` and `POST /api/workflows/approvals/{id}/approve` / `reject` are removed. List with `GET /api/workflows/approval-inbox`; decide with `POST /api/confirmations/{id}/respond`, as for any other approval request.
- **Behavior change: `send_notification` sends to your organization's channels, and the instance-wide webhook variables are deprecated.** The tool (offered only with `NOTIFICATION_TOOL_ENABLED=true`) posted to whichever of `SLACK_WEBHOOK_URL`, `LARK_WEBHOOK_URL` and `WECOM_WEBHOOK_URL` the operator had set, the same webhooks for every user and organization on the instance, or mailed any allowed address. It now takes a `channel`: the name or id of an enabled channel in an organization the calling user belongs to (Settings → Channels), and lists those channels when none is named. It acts for the person chatting, or for the user a workflow run acts for, whichever agent it is used through. The three variables keep working for one more release as `instance:slack`, `instance:lark` and `instance:wecom`, selectable by every user as before; recreate each as a webhook channel in the organization that should receive it, update agent instructions that name a provider, and remove the variable. The `provider` parameter is gone. A call that still passes `slack`, `lark` or `wecom` is routed to the instance webhook, also when it passes free text such as `#general` as `channel`, which those providers always ignored; if `channel` names one of your channels, that channel is used. The tool no longer takes an email address: a call with `provider: email` and an address is answered with a hint to send to an email channel or use `email_send`.
- **Behavior change: with billing off, the token limit that is enforced is the one the Usage card shows.** On an instance whose access model is `off`, a user who still had a plan left on their account from a time billing was on was held to that plan's monthly quota, while Settings → Usage showed the instance default. Chat, the AI-assisted builders, knowledge-base and database chat, eval runs and workflow runs now enforce the instance default (`default_token_quota`; unset or 0 means unlimited) for such users, the same number the card shows. A user with an admin-set quota keeps it. Instances with billing on are unaffected.
- **Behavior change: a shared workflow uses connectors, MCP servers and knowledge bases on its author's access, not the runner's.** Connector, MCP and Knowledge Retrieval steps checked whether the person running the workflow could see each resource, so someone running a shared workflow needed their own subscription to every connector and MCP server in it, and a Knowledge Retrieval step returned nothing (with no error) for anyone but the knowledge base's owner. A step now works for whoever runs the workflow as long as the workflow's author can still use the resource and it is switched on: for a knowledge base, the author owns it. When the author loses access (the resource is unpublished, the author's subscription is removed, or it is switched off) the step fails for everyone, including a runner who can still see the resource themselves. Credentials are unchanged: a connector or MCP step still uses the runner's own saved credential, or the owner's when the owner allows fallback, and is refused otherwise. A Knowledge Retrieval step that names a knowledge base that cannot be used now fails with the reason instead of returning an empty result, and a Connector step that names someone else's database connector says it can only be used by its owner.
- **Who may decide an approval request is fixed when it is created.** The approver scope was read from the agent's settings at the moment someone clicked Approve, so changing "Approver scope" moved requests that were already waiting, and a request with no agent behind it could not be decided at all. Each request now records who may decide it (the person who asked, the agent's owner, or the organisation's members) when it is created, and the portal card and the Feishu card both read that. Changing the agent afterwards affects the next request, not the one on screen. A Feishu click from a linked FIM One account that has since been disabled is denied like an unlinked one. The Approval Playground card can be decided by the person who sent it (with a linked Feishu account); its clicks were refused because the test request has no agent.
- **A waiting approval request closes when its own time is up.** The background sweep marked a pending request expired once it was a day old (`CHANNEL_CONFIRMATION_TTL_MINUTES`), whatever its own window. A request now closes at the deadline it was created with: a Feishu card for a chat tool call that nobody answered within its two minutes stops accepting clicks at that moment instead of a day later (a late Approve or Reject, in Feishu or the portal, is answered "expired" even before the sweep has marked the request), and a request with a longer window is not cut short by the sweep. Requests written before this release have no deadline recorded and keep the day limit.
- **Workflow approvals are approval requests like any other, and an assignee must belong to the organisation.** A Human Intervention step used to record its approval in a table of its own with its own rules. It now creates an approval request through the same service as a chat confirmation: assigned to one person, or to whoever the run belongs to, and nobody else; the workflow's author cannot decide an approval in a run someone else started. A platform administrator can decide any approval, as for chat confirmations. The step's "Assignee" is written as a user ID, a username or an email address and must name one active user in the workflow's organisation (for a workflow published to none, a user who shares an organisation with the person running it); a literal assignee is checked when the workflow is saved and again, against the target organisation, when it is published to one (`approval_assignee_not_in_org`, naming the step) and a `{{variable}}` when the run fills it in, failing the step. The approval endpoints under `/api/workflows/approvals` answer as before; approvals recorded before this release in the old table are no longer listed.
- **Human Intervention workflow steps are off unless the operator enables them.** With `WORKFLOW_HUMAN_INTERVENTION_ENABLED` unset, the editor does not offer the step, saving or importing a workflow that contains one is refused with `human_intervention_disabled`, and a stored workflow that contains one opens for editing but is refused at run start. Set it to `true` to use approval steps.
- **Batch workflow runs count toward your concurrent-run limit.** Batch items ran outside the limit of 3 concurrent runs per user, so one batch could run 10 at a time on top of it. Each item now takes a slot from the same limit and waits for one instead of failing, and a batch leaves one slot free, so runs you start by hand still start while a batch is in progress. A batch may therefore run fewer items at once than its "Max Parallel" setting. Submitting a batch counts as one start against the runs-per-minute limit.
- **In a workflow MCP step, your saved MCP credential replaces the server's values instead of being combined with them.** When you were the server's owner or the owner allowed fallback, the step sent your saved environment variables or headers on top of the server's own, so a value you had not set yourself (a second header, a region variable) still came from the server. The step now sends only what you saved, as chat already does. If a server needs values besides the secret, add them to your own credential under "Configure My Keys".

### Security

- **An admin who unpublishes someone else's resource is no longer answered with its contents.** Unpublish is open to the owner, to an admin of the organization the resource is shared with, and to a platform admin, and it answered all three with the owner's view. An org admin unpublishing another member's MCP server received its URL, command, launch arguments and the decrypted values of its environment variables and headers; for a connector the base URL, actions and configuration; for an agent its instructions and model settings; for a workflow its blueprint and webhook URL; for a skill its content and script. Only the owner now receives those; anyone else gets the same reduced view the list shows them. Rotate any credential stored on a shared MCP server that someone other than its owner has unpublished.
- **Behavior change: an MCP server whose address or launch arguments contain a credential is its owner's alone while "Allow credential fallback" is off.** With fallback off, other users connect to a shared MCP server with their own environment variables or headers, never the owner's. The server's URL and its stdio launch arguments are always the owner's, though, so a token the owner had put there (`https://host/mcp?token=…`, `https://user:pass@host/…`, `--api-key sk-…`) went out for every other user, who only had to save any credential of their own to be let in. Such a server is now refused to everyone but its owner with `mcp_server_address_private` (403): in chat, for delegated agents and in a workflow Agent step its tools are absent; a workflow MCP step fails with the reason; the step editor's tool list answers the code. A URL counts when it has user-info, a query string or a fragment; launch arguments count when one is a flag, assignment or header with `token`, `key`, `secret`, `password`, `auth`, `credential` or `bearer` as a whole word of its name (`--api-key`, `API_KEY=`, `X-Api-Key:`; not `--keyboard-layout`, `--max-tokens`, `--no-auth` or `--key-file`), a URL that counts by the URL rule, or a known token shape (`sk-…`, `ghp_…`, `xoxb-…`, an AWS key id, a JWT, `Bearer <token>`, any UUID or long opaque value), Docker's `-e NAME=VALUE`, or a connection string with a password. A URL also counts when a path segment is shaped like a token, as hosted automation servers write it (`https://mcp.zapier.com/api/mcp/s/<secret>/mcp`, `https://host/<32 hex>/sse`): a UUID, 16 or more hex digits, 20 or more characters mixing letters and digits, a known token prefix, or a `;name=value` path parameter. The fixed addresses of well-known servers (GitHub, Linear, Notion, Sentry, Atlassian and the like) are not flagged. The path rule is a guess by shape, so the messages say the address *may* contain a credential; a short or worded secret segment, or a bare argument, is not recognised. The owner is unaffected, and so is a server with fallback on. Other users see "Only its owner can use this server" on the card instead of being asked to configure keys. "Configure My Keys" is not offered for such a server, the Market says so before you subscribe, and a solution that depends on one lists it apart from the dependencies that need your keys. **Upgrade note:** a shared server of this kind with fallback off stops working for its subscribers on upgrade. Its owner sees a warning on the server's card, in its editor and when saving or publishing it (also for a personal server that one of the owner's shared agents or workflows uses), naming the part that counted (the query string, a path segment, an argument name; never the value), and either moves the credential into a header or an environment variable (others then bring their own) or switches fallback on (others without credentials of their own then use the owner's: the address, and the headers and environment variables saved on the server). See [Credential Fallback](/architecture/organization#credential-fallback).
- **The HTTP client's request log no longer prints credentials carried in URLs.** At the default log level the HTTP libraries write one line per request with its full URL, and the MCP SDK writes the traceback of a failed connection with the URL in it. An MCP server address such as `https://user:pass@host/mcp?token=…`, a connector base URL with a key in its query string, or a webhook URL whose secret is a path segment therefore ended up in the server log on every call. The records of `httpx`, `httpx2`, `httpcore` and the MCP SDK are now stripped of user-info, query string, fragment and token-shaped path segments before they are written, in every worker process.
- **Logs and error messages no longer quote the credential in an MCP server's URL or launch arguments.** Connecting to an MCP server logged its full URL and its launch arguments, and a failed connection put the error, which names the URL with its query string and user-info, into the server log, into the failed workflow MCP step, and into what an MCP tool answers in chat (whether offered through the `mcp` tool, as a tool of its own, or to a delegated agent). A user the owner lends the server to is never shown its address, yet could read the token there. URLs are now logged and reported without user-info, query string and fragment, and launch arguments are counted, not printed. A path segment shaped like a token (`/api/mcp/s/<secret>/mcp`, a webhook's `/hook/<uuid>`) is printed as `***`, in call records as well. "Test connection" still shows the owner the error as it is.
- **A read-only MySQL or MariaDB connector could still write a file where the check and the server read a statement differently.** MySQL starts a `--` comment only before an ASCII space or control character, and treats U+3000, U+00A0 and U+0085 as part of a name; the read-only check asked Python, which calls those white space and U+007F not. A statement built around that difference (`SELECT 1 --<U+007F>'` … `INTO OUTFILE '/tmp/x'`) hid `INTO OUTFILE` from the check, and the server ran it. On a server whose global SQL mode has `NO_BACKSLASH_ESCAPES`, a backslash before a quote did the same (`SELECT '\' , LOAD_FILE(…) , '\'`). The check now follows the servers' byte rules (ASCII letters, digits and white space only; every non-ASCII character is part of a name; names are case-folded in ASCII only), and a read-only connector on any database refuses a control character other than tab and line breaks, and any non-ASCII space or invisible character, outside quotes. Inside a comment the non-ASCII ones are accepted on PostgreSQL and MySQL (a full-width space in a Chinese comment, an emoji's joiner): where a comment ends is decided by ASCII alone. Every read-only MySQL session is put into the server's SQL mode without `NO_BACKSLASH_ESCAPES` and `ANSI_QUOTES` (and the combination modes that imply the latter, such as `ANSI`), so strings end where the check expects. Behavior change on a server that runs in `ANSI_QUOTES` or `NO_BACKSLASH_ESCAPES` mode, for read-only connectors only: `"name"` is a string and a backslash escapes, as in MySQL's default mode; write names with backticks. A read-write connector keeps the server's own mode, so its existing SQL means what it did.
- **On MySQL a bound number or boolean no longer matches every row of a text column.** MySQL compares a number with a text column by turning each row's text into a number, and text that is not a number counts as 0. A workflow step's `WHERE api_token = {{token}}` therefore returned every row when the variable held the number `0` or `false`, a value a trigger caller can send. On MySQL and MariaDB every bound value is now sent as text (`0` as `'0'`, `true` as `'1'`): against a text column it is compared as text, against a numeric column MySQL still compares by value. The other direction is MySQL's own leniency and is not changed: text compared with a numeric column is converted by MySQL (`'5abc'` counts as 5, other text as 0), so validate an input that must be a number in a Condition step before the query; the Start step does not check input types. The one exception is right after `LIMIT` and `OFFSET`, where MySQL takes only a bare whole number: there the value must be a whole number that is not negative, and the step fails otherwise. PostgreSQL was not affected.
- **A MySQL or MariaDB connector no longer carries session state from one query to the next, and bound values no longer depend on the session's character set.** Connections are pooled, and a connection kept whatever the last query left on it: user variables, named locks, `sql_mode` and the client character set. After `SET NAMES gbk` (an ordinary statement on a read-write connector) the next query on that connection ran in gbk, where escaping a quote is not safe, and a value bound into a workflow step's SQL could break out of its string (`縗' OR 1=1 -- ` returned every row). Each query now starts on a reset session (`COM_RESET_CONNECTION`, MySQL 5.7.3+ and MariaDB 10.2.4+, followed by the connector's character set, `utf8mb4` unless its settings name another); on an older server connections are not reused at all. The session is cleared again when the query is done, so a named lock (`GET_LOCK`) or a temporary table is not held while the connection waits in the pool; a read-only connector refuses the lock functions (`GET_LOCK`, `RELEASE_LOCK`, `IS_FREE_LOCK`, `IS_USED_LOCK`, and PostgreSQL's `pg_advisory_*`) altogether. A connection is given back to the pool whatever happens between checkout and release, a cancelled request included (a connection that is cut off in the middle of a reset is closed, not reused). The connector's database is selected again as well: `USE other` on a read-write connector applies to that one statement and no longer moves every later query on the pooled connection to the other database (a read-only connector refuses `USE`). Write `other.table` to read another database. (A connector with no database configured has none to go back to: a connection on which `USE` chose one is not reused.) Bound text is no longer escaped: it is written as a hex literal (`_utf8mb4 X'…'`), which reads the same in any character set and SQL mode.
- **A read-only PostgreSQL connector refuses functions that act outside the query.** A read-only transaction stops writes to tables, not functions that reach past it. With a database account privileged enough, `dblink_exec` wrote through a second connection, `pg_read_file` and `pg_ls_dir` read the server's files, `lo_export` wrote one, and `pg_terminate_backend`, `pg_reload_conf`, `pg_switch_wal` and `pg_sleep_for` ran. A read-only connector now refuses a call of `dblink*`, `pg_read_*`, `pg_ls_*`, `lo_import`, `lo_export`, `pg_sleep*`, `pg_terminate_backend`, `pg_cancel_backend`, `pg_reload_conf`, `pg_switch_wal`, `pg_rotate_logfile`, `pg_stat_reset*`, `pg_create_restore_point`, `pg_logical_emit_message`, `pg_stat_file`, `pg_current_logfile`, `ts_stat`, the `query_to_xml`/`table_to_xml`/`cursor_to_xml`/`database_to_xml`/`schema_to_xml` family (they run query text of their own), the replication-slot and replication-origin functions, and `set_config`, except `set_config('<name>', value, true)` (for the current transaction only, which a read-only connector rolls back) where the name is written out as a string and is one of `search_path`, `datestyle`, `timezone`, `intervalstyle` or `extra_float_digits`; settings that change what a query may do (`statement_timeout`, `lock_timeout`, `role`, `session_authorization`, `row_security`, the `transaction_*` settings) stay refused. `U&'…'` strings are allowed; `U&"…"` names and the `UESCAPE` clause are not. Also refused: `pg_notify`, `pg_export_snapshot`, `pg_promote`, the backup functions (`pg_backup_start`/`pg_backup_stop`, `pg_start_backup`/`pg_stop_backup`), `pg_wal_replay_pause`/`pg_wal_replay_resume`, `pg_import_system_collations` and `pg_log_backend_memory_contexts`. Three ways around the list are closed by reading the statement exactly as PostgreSQL does: a `--` comment ends at a carriage return as well as at a newline, a non-ASCII character is part of a name (so `$$` after an emoji does not start a string, and a dollar-quote tag may itself be non-ASCII), and `U&"…"`, which spells a name with `\XXXX` escapes, is refused on a read-only connector. The query timeout is now also enforced on the client side, and a query the server stops for running too long is reported as a timeout. Only a call is refused: a column or a string with one of these names is not. This is a list of known names, and the database has others; the fence that holds is the connector's database account. Use one that can only `SELECT` what the connector should see, without superuser, file-access or replication rights.
- **A read-only MySQL or MariaDB connector could be made to run DDL and administration statements through a `/*! … */` comment.** MySQL runs the inside of such a comment as SQL. The read-only check skipped it as a comment, saw the `SELECT` after it, and let `/*!CREATE TABLE x AS*/ SELECT …`, `/*!DROP TABLE …*/`, `TRUNCATE`, `RENAME`, `ALTER VIEW`, `CREATE USER`, `GRANT` and `SET GLOBAL` through; MySQL's read-only transaction does not stop these (it is committed before DDL, and `SET` is allowed in it). This applied to chat, the query box on the connector's page and workflow steps. A read-only connector now refuses any `/*! … */` or `/*M! … */` comment, and every rule of the check (first keyword, more than one statement, `INTO`, refused functions) is applied to the statement as the connector's own database reads it, with comments and strings removed, never to the raw text. The same change removes refusals of ordinary reads: a column or alias called `update`, `delete` or `merge`; a string that contains `sleep(`, `benchmark(` or `load data`; a `;` inside a comment or a string; a backslash before a quote next to the word `delete`; `(SELECT …) UNION (SELECT …)`, `TABLE t` and `VALUES (…)`; a leading `#` comment on MySQL; an alias such as `replace` or `create` after a function call in a `WITH` clause. On DM8, which has no read-only transaction behind the check, `INSERT`, `UPDATE`, `DELETE` and `MERGE` are still refused anywhere outside quotes, also as a column or alias.
- **A read-only database connector can no longer be written through.** The read-only switch was enforced by looking at the first word of the SQL, so three kinds of statement that begin like a read still changed data: a write inside a `WITH` clause (`WITH d AS (DELETE … RETURNING …) SELECT …`), `EXPLAIN ANALYZE` of a write (it runs the statement it explains), and `SELECT … INTO` (it creates a table). This applied wherever the connector is queried: chat, the query box on the connector's page and workflow steps. A read-only connector now runs every query in a read-only transaction, so the database itself refuses the write: on PostgreSQL, KingbaseES and HighGo in a `READ ONLY` transaction that is always rolled back; on MySQL and MariaDB between `START TRANSACTION READ ONLY` and `ROLLBACK`, which refuses row changes (MySQL does not refuse `CREATE`/`DROP`/`ALTER` there, and those are refused by the check on the statement's first word, as before). The check that runs first is stricter too, for every database type: on a read-only connector it refuses `INSERT`, `UPDATE`, `DELETE` and `MERGE` anywhere in a query, `SELECT … INTO`, and `EXPLAIN ANALYZE` of anything but a `SELECT`; keywords inside strings and comments are not counted, and a comment can no longer hide one. Where databases disagree about what is a string or a comment (`#`, `$$`, a backslash before a quote), the SQL is read the way the connector's own database reads it, and both ways for the backslash. DM8 has no read-only transaction in this release and relies on that check alone. Behavior change on read-only connectors: `SELECT … FOR UPDATE`, `FOR SHARE`, `FOR KEY SHARE` and MySQL's `LOCK IN SHARE MODE` are refused, and so is `:=` on MySQL (it sets a session variable), and a query that calls a function which writes (`nextval()`, a function that inserts an audit row) now fails; switch the connector to read-write if it needs to do that. Connectors with read-only switched off are not affected.
- **Behavior change: a workflow started with a trigger key reports a failed run with a code and a fixed sentence.** `POST /api/workflows/trigger` answered a failed run with the engine's own text in `error`: the ids of the steps that failed, or the message of an internal exception. Whoever holds the key is not a signed-in user, so the response now carries `error_code` (`workflow_step_failed`, `workflow_run_timed_out`, `workflow_run_cancelled` or `workflow_run_failed`) and a fixed sentence for that code in `error`. Which step failed and what it said (a database's error message, for example) is in the run history, which the workflow's owner can read. An integration that parsed step ids out of `error` should read `error_code` instead. A run that is refused because the saved workflow is invalid is answered the same way: `invalid_blueprint` and a fixed sentence, where the response used to quote the fault and the step it is in.
- **Text in a notification can no longer notify the members of a chat.** A completion summary quotes the user message and the answer, and `send_notification` posts what a model wrote. That text went into Slack `mrkdwn` and Lark / Feishu card markdown as it was, so `<!channel>`, `<!here>`, `<@U…>` in Slack, `<at id=all></at>` in Lark / Feishu and `<@userid>` in WeCom pinged people, and a Slack `<url|label>` could show a link under another label. Slack bodies are now escaped (`&`, `<`, `>`), so such sequences appear as written; a notification that relied on `<url|label>` shows it literally, and a plain URL is still linked by Slack. In Lark / Feishu (webhook cards, and the Feishu app's text notices, completion cards and approval cards) and WeCom the mention tags are shown as text and no longer parsed.
- **Text sent to an email channel can no longer carry HTML.** A notice mailed to an email channel went out with its body as HTML exactly as written. That body is what a model passed to `send_notification`, so a page or document the agent had read could make it mail the channel's recipients a link under another label, a remote image or a form; only the completion notification escaped its text. The body of every notice is now escaped the way the completion notification's is: tags arrive as the characters that were typed, `**bold**` is still rendered and line breaks are kept (they used to collapse into one paragraph). This covers `send_notification`, the channel's "Send Test Message" and the admin notification endpoints; an admin who posted HTML through `POST /api/notifications/send` to the email provider now sees it delivered as text. The subject is unchanged.
- **The email recipient allowlist can no longer be passed with text that only ends in an allowed address.** `SMTP_ALLOWED_DOMAINS` / `SMTP_ALLOWED_ADDRESSES` were checked against what follows the last `@` of each comma-separated item, so `<victim@other.com> a@allowed.com`, `x@other.com@allowed.com` or `x@other.com;a@allowed.com` counted as allowed while the mail server delivered to the other address. This held for the `email_send` tool (`to`, `cc`, `bcc`) and for the recipients of an email channel. Each recipient must now be exactly one plain address (`name@example.com`): display names, angle brackets, spaces, semicolons, parentheses, a second `@`, control characters and non-ASCII characters are refused, by the tool with "Not a valid email address" and by a channel with `channel_email_recipients_invalid`. An email channel saved earlier with such text sends nothing until its recipients are corrected. Write `Name <a@b.com>` as `a@b.com`.
- **A Feishu app channel only calls Feishu's own API address, or one the operator listed.** A Feishu channel's config accepts a `base_url` (settable through the API, not in the form). It was not checked, so an organization admin could point it at any host the server can reach, internal ones included; any member pressing Test then made the server post the app credentials there, and the host's answer came back in the error message. `base_url` must now be empty, `https://open.feishu.cn` or `https://open.larksuite.com`; any other value is refused when the channel is saved (`feishu_channel_base_url_not_allowed`) and a channel saved earlier with one sends nothing and says why. Error messages from a Feishu channel now carry Feishu's numeric error code only; the full answer is written to the server log. **Upgrade note for a privately deployed Feishu:** list its API origin in the new `FEISHU_ALLOWED_BASE_URLS` (comma-separated, https only, for example `https://open.feishu.example.com`) before upgrading, or its channels stop sending and approval cards are not delivered.
- **The Feishu group picker asks the channel's own Feishu address.** "Pick a group" in the Feishu app channel form always called `https://open.feishu.cn`, whatever the channel's `base_url`. For a privately deployed Feishu it therefore listed nothing, and each attempt posted that deployment's app ID and app secret to feishu.cn. The picker now calls the address the channel itself uses: the saved channel's `base_url` when editing, and the `base_url` sent with the request to `POST /api/channels/discover-chats` when creating one through the API (the form has no such field and keeps using open.feishu.cn). A saved app secret is only sent to the address saved with it. An address the channel could not be saved with is refused with `feishu_channel_base_url_not_allowed` before anything is sent. If you ever opened the picker for a private deployment's channel, consider rotating that app's secret.
- **An agent's completion notification only goes to a channel of its own organization.** An agent can post the user's message and its final answer to a channel when a run finishes. The channel was not checked when the agent was saved, and at send time only an agent published to an organization was compared with the channel's organization, so a personal agent could be pointed, through the API, at any organization's channel by its id. The notification is now sent only to an active channel of the agent's organization, or for a personal agent of an organization its owner belongs to, the rule approval channels already follow. Saving an agent with a completion channel from an organization you are not a member of is refused with HTTP 403 `completion_channel_denied`. An agent already pointing at such a channel keeps running and stops notifying.
- **Workflow runs, delegated agents and evaluation runs no longer share one directory for their shell, code-execution and file tools.** An agent run by a workflow Agent step, an agent delegated to with `call_agent`, and an evaluation run had `shell_exec`, `python_exec`, `node_exec` and `file_ops` working in a fallback directory used by every such run of every user and organisation (a directory of the host itself when no Docker sandbox is configured), so one run could read and change the files another had left. Each workflow run and each evaluation run now has a directory of its own, removed when the run ends, whether it finished, failed or was cancelled; a file one Agent step writes is there for the later Agent steps of the same run and for nothing else. An agent delegated to from a conversation works in that conversation's directory, on the same files a chat with it there sees. A chat request sent without a conversation id no longer gets these four tools.
- **A workflow Agent step with no agent selected no longer gets the shell, code-execution or file tools.** An Agent step whose "Select agent" field is empty runs a plain model with built-in tools. That set included `shell_exec`, `python_exec`, `node_exec` and `file_ops`, running in a directory shared by every such run (on the host itself when no Docker sandbox is configured), unattended, on input that a trigger caller can supply. The step now gets the built-in tools without those four, without image generation and the knowledge-base tools (`generate_image`, `kb_list`, `kb_retrieve`), without the mail and notification tools (`email_send`, `send_notification`), and without any tool an administrator has disabled. To run code or send a message from a workflow, select an agent whose tools include it.
- **A workflow Agent step fails when its agent cannot be used, instead of running without it.** If the agent in an Agent step had been deleted, unpublished or was otherwise not available, the step ran anyway as a plain model with every built-in tool and no approval gate; an agent its owner had switched off kept running. The step now fails with the reason ("not found or not accessible", "is disabled"). Whether the agent is available is judged for the workflow's author, so someone running a shared workflow does not need their own subscription to the agents in it, and when the author loses access the step fails for everyone.
- **Auto mode checks the conversation, the quota and the agent before it asks a model how to route.** In Auto mode the message was first sent to the fast model to choose between Standard and Plan, and only then checked. A user over their token quota (or with no plan where one is required) spent that one model call before being refused, and a message sent to someone else's conversation id was answered with the state of that conversation's agent instead of "conversation not found". The checks now come first, as in the other two modes.
- **A plan or quota check that fails refuses the request instead of letting it through.** When reading a user's plan failed (a database error), the check treated the user as entitled, and a failed plan-quota lookup fell back to the instance default, which is unlimited when unset. A model call is now refused with HTTP 503 `quota_unavailable` ("Your plan and token quota could not be checked. Try again shortly.") until the lookup works again.
- **A conversation whose agent is no longer available stops instead of carrying on without it.** When the agent a conversation was started with had been unpublished, your subscription to it removed, or it had been switched off, the next message went through as a chat with no agent: the agent's instructions and bindings were gone, every connector and MCP server you can use was attached instead, and nothing asked for confirmation. Sending a message in such a conversation is now refused with `agent_unavailable` and the advice to start a new conversation; this applies to the agent's owner as well when the agent is switched off, as it does for every other resource. Starting a new chat with an agent you can no longer use answers `resource_not_found` or `resource_inactive`.
- **In a chat with no agent, an action marked "requires confirmation" asks first.** Such a chat offers every connector you can use, and a connector action its owner marked as requiring confirmation ran at once, because the confirmation gate stepped aside when no agent was selected. The same approval card now appears in the chat and you decide it yourself; the action runs on Approve and is refused on Reject or after two minutes without an answer. The card is shown in ReAct and in Plan (DAG) mode.
- **A Feishu channel can only decide the approval requests it delivered.** The callback of any channel accepted a click on any request, so an organisation that had configured a channel of its own could, knowing a request's id and the approver's Feishu id, decide a request another organisation's channel had sent. A click now counts only for a request the receiving channel carried; for anything else the card shows "Confirmation request not found". Requests shown only in the portal cannot be decided from a channel at all.
- **A personal MCP credential that does not fit the server's transport no longer borrows the owner's.** When the owner of a shared MCP server switches "allow fallback" off, other users are meant to connect with their own credential or not at all. A personal credential holding only environment variables was accepted for an SSE or HTTP server, which reads headers, and the connection went out with the owner's headers, access token included. A personal credential now counts only when it supplies what the server's transport reads (environment variables for stdio, headers for SSE and HTTP). Without one, the server is left out of the chat, and a workflow MCP step fails with a message naming what to save. Such a user's values are no longer combined with the owner's, and a failed credential lookup refuses the connection instead of using the owner's credentials. Owners, and servers with fallback on, are unaffected.

- **Personal credentials for an SSE or HTTP MCP server are entered as request headers.** "Configure My Keys" offered only environment variables, which those servers do not read, so the portal had no way to give them a personal credential. The form now shows request headers for SSE and HTTP servers and environment variables for stdio servers. Saving a credential the server's transport does not read is refused (`mcp_credential_needs_headers`, `mcp_credential_needs_env`), and a server whose saved credential does not fit shows "Configure keys to use this tool" again. Headers saved this way are used in chat on every server, including for the owner and on servers with fallback on, where chat ignored a headers-only credential and sent the server's own.

- **A saved credential that can no longer be decrypted is refused instead of being treated as absent.** A stored connector or MCP credential that cannot be decrypted (for example after the encryption key changed) was read as empty. Depending on the case the call then went out with no credential, or with the owner's in place of your own, and the record showed nothing unusual. Such a call is now refused with a message to try again, in chat (the tool is left out) and in workflow steps (the step fails), until the credential is saved again.

- **A failed credential lookup no longer falls back to the owner's MCP credentials.** When reading your saved credential for an MCP server failed (a database error), chat and the workflow MCP step connected with the credentials stored on the server if you were its owner or the owner allowed fallback, so a call meant to go out under your own account could go out under the owner's. The server is now left out of that chat turn, and a workflow MCP step fails with a message to try again.

- **A workflow connector step is refused when the person running it has no credential for the connector.** If you ran a workflow whose connector step used a shared connector, had saved no credential of your own, and the owner had switched fallback off, the step sent the request with no credential and left the outcome to the remote service. The step now fails with a message asking you to save your own credential, as the same connector already behaves in chat.

- **Chat without an agent uses connector credentials, and records its calls.** With no agent selected, connector actions were sent with no credential at all: a personal credential and the one stored on the connector were both ignored, so a service that requires authentication refused the call, for the connector's owner too. Calls now go out with the same credential as in a chat with an agent: your own if you saved one, otherwise the owner's when you are the owner or the owner allows fallback. A shared connector whose owner switched fallback off is no longer offered in such a conversation until you save your own credential; it used to be offered and called unauthenticated. Connector and database calls made there are now written to the call log, and a database call records the read-only and column-masking rules it ran under.

### Fixed

- **Every action in Admin → Audit Log has a readable name.** 42 actions that were already recorded (model groups and providers, billing plans, batch operations, workflow templates, eval cleanup, Market moderation) were shown by their internal name, such as `model_group.deactivate_all`.
- **Workflow editor: right-click Duplicate copies the step you clicked.** It copied whichever step was selected, or nothing when none was.
- **Workflow editor: clicking or selecting is no longer an undo step.** Undo stepped back through selections and was enabled right after opening a workflow.
- **Workflow editor: pan and zoom are remembered.** The canvas reopened fitted to the whole graph every time. Where you left it is now saved with the workflow; moving the view alone creates no version and does not send a published workflow back to review.
- **Workflow editor: Test Node and Batch Run use what is on the canvas.** Like Run, both went to the server with whatever was last saved; an edit made in the last few seconds was not in what ran. Both now save first and do not start if that save fails.
- **The schedule dialog shows the schedule you saved.** Reopened, it showed an empty expression, the default time zone and no inputs, and the toolbar did not mark an active schedule.
- **Workflow editor: Run uses what is on the canvas.** Clicking Run within a few seconds of an edit ran the previously saved graph. Run now saves first, and does not start if that save fails.
- **Times shown as "about 8 hours ago" for something just created.** On instances whose database returns timestamps without a zone, version history, run history and other lists read them in the browser's local time. They are read as UTC.
- **A database query that is given up on is stopped on the MySQL server too.** When a query to a MySQL or MariaDB connector timed out on the client or its request was cancelled, the connection was dropped and the statement ran on in the server for as long as it took; repeated timeouts could leave any number of them running. The connector now sends `KILL QUERY` for the abandoned statement from a short-lived connection of its own, and counts the statement against the connector's five connections until the server reports it gone (or ten times the query timeout has passed). While all five are taken, a new query waits for one for at most its own timeout and is then told "all 5 connections of this connector are busy" instead of adding to the pile. A few statements (large `information_schema` scans, for example) take MySQL a long time to interrupt even when killed. PostgreSQL already cancelled such a query on the server.
- **Opening an MCP Tool step no longer asks the MCP server for its tools every time.** The editor asked the server each time the step was selected, and the API kept a database connection in use for as long as the server took to answer (up to 30 seconds), so a slow server and a few open editors could use up the connection pool. The database connection is now released before the server is contacted. A listing is reused for 30 seconds, for the same user only and only while the server's settings and the credential it is opened with are unchanged; selecting the same step again within that time shows the tools at once, and Retry always asks the server. A user can have three listings in progress at a time; one more is answered with `mcp_tools_busy` (HTTP 429).
- **Agent, Knowledge Retrieval and MCP Tool steps are pointed at their resource with a dropdown.** Each of these workflow steps had a text field for an internal id that had to be copied from another page. The Agent step now lists the agents you can use (with "No agent (plain model)" for none), the Knowledge Retrieval step your own knowledge bases, and the MCP Tool step the MCP servers you can use; switched-off ones are not listed. A step that already points at something that is no longer listed keeps showing it. Workflows saved earlier open unchanged. Choosing another MCP server clears the step's tool.
- **Importing a workflow warns about every resource its steps will not be able to use.** The import check counted a reference as fine whenever you could see the resource. A connector, MCP server, agent or knowledge base that is switched off, and a database connector someone else owns, passed the check and then failed at the first run. The check now applies the rule the steps apply when they run, so these are counted in the "unresolved references" notice and listed in the import response's `unresolved_references` and `warnings`, with the reason ("is disabled", "can only be used by its owner"). The workflow is still imported.
- **An agent can no longer be bound to two connectors, or two MCP servers, that would share tool names.** Tool names are derived from the resource name: for a connector lower-cased with every character other than a letter or digit turned into `_`, for an MCP server with every character outside letters, digits, `_` and `-` turned into `_`. Two bound resources with the same result (`CRM` and `crm!`, or two MCP servers both called `docs`) collided when the agent ran, and the order they were bound in decided which one kept the plain name, so a call could reach the other system. Saving an agent with such a pair is now refused with HTTP 400 `agent_connector_names_collide` or `agent_mcp_server_names_collide`, naming both; rename one or bind only one. An API connector and a database connector may still share a name. The check runs when an agent is created and when its connector or MCP server list changes: an agent that already has such a pair keeps running as before and can be edited otherwise, but changing that list is refused until the pair is resolved.
- **Plan mode runs the number of rounds `DAG_MAX_REPLAN_ROUNDS` says.** The setting counts planning rounds in total: the first plan plus N−1 autonomous re-plans. A goal that was not reached was re-planned one time fewer than that, so the default of 3 gave two rounds (one re-plan) and a value of 2 never re-planned. The default now gives three rounds (two re-plans). A run whose goal is still not reached therefore costs one more round of model calls than before; set `DAG_MAX_REPLAN_ROUNDS=2` to keep the previous count. Re-plans triggered by a message you send during a run were never counted and still are not.
- **A channel chosen for an organization agent is checked against that organization when the agent is saved.** For an agent that belongs to an organization, a completion notification (and an approval request) is only sent through a channel of that organization. Saving accepted a channel from any organization you are a member of, so a channel from another of your organizations was saved and then never used. Saving now refuses it with `completion_channel_not_in_agent_org` or `approval_channel_not_in_agent_org`. An agent with no organization is checked against your memberships as before, and a binding saved earlier does not block other edits.
- **An agent cannot be saved with an approval channel that cannot carry approvals.** The agent form offers only Feishu app channels for approvals, but the API accepted any channel of your organization, a webhook or an email channel included. Such a channel has no way to bring a decision back, so at run time it was treated as no channel at all. Saving an agent with one as its approval channel is now refused with `approval_channel_type_unsupported`. An agent saved earlier with such a binding can still be edited; the binding is refused when it is changed to another channel of that kind.
- **A notification title or mail subject with a line break is sent on one line.** A title passed to `send_notification`, or a subject passed to `email_send`, that contained a line break made delivery through an email channel fail with a header error. Line breaks and control characters in a title or subject are now collapsed to a single space, for every channel type.
- **A completion email shows the message and the answer as text.** The completion notification sent through an email channel is an HTML mail, and the user message and the final answer were put into it unescaped, so `<` and `&` were lost and markup in either was rendered by the mail client, links and images included. Both are now escaped; the labels (`**Duration**` and the others) are shown in bold instead of with their asterisks.
- **The quota line on the Usage card counts workflow runs, as the limit does.** Tokens spent by workflow runs count toward your token quota, but the "used" figure and the percentage in Settings → Usage and on the Billing tab added up conversations only, so an account could be refused for being over quota while the card showed room left. Both now show the number the limit is checked against. The total, daily and per-agent figures above it still cover conversations only.
- **An agent in a workflow Agent step can use its MCP servers, and its calls are recorded under the run.** The step ran the agent with its connectors and knowledge bases but never connected the MCP servers bound to it. They are now connected for the step (with the credential of whoever runs the workflow) and released when it ends. Connector, database and MCP calls the agent makes carry the workflow run they belong to in the call log.
- **An agent you delegate to from a chat with no agent can use its MCP servers.** In a chat with no agent selected the model can hand a task to one of your agents. That agent ran with its connectors and knowledge bases but without the MCP servers bound to it, so a task that needed one of their tools could not be done. The delegated agent is now set up the way a chat with it is, MCP servers included; your own saved credential for a server is used when you have one. An agent that was switched off or unpublished after the chat started is reported as unavailable instead of being run.
- **An MCP server cannot be saved with a transport that does not exist.** The API accepted any text as the transport, so a server created through it with, say, `http` or `SSE` was stored, could never be connected, and refused every personal credential with a message about request headers. Creating or updating a server now accepts only `stdio`, `sse` and `streamable_http`.
- **Approval cards appear in Plan (DAG) mode.** A tool call that needed approval inside a plan step showed no card in the chat, with or without an agent, so the step waited two minutes and the call was refused. The step now shows the same approval card as ReAct mode, where you approve or reject, and the card stays in the transcript afterwards. A request left unanswered by an earlier turn no longer shows up as a card in the next one.
- **Two approval messages say what happened.** A tool call refused because the agent is set to "Channel only" with no usable approval channel now says so in the words of the agent editor and points to the setting, instead of naming the stored value `channel_only`. Clicking a Feishu approval card with a linked account that has been disabled answers "Your linked FIM One account is disabled" instead of "no longer exists".
- **Deleting a workflow run closes the approvals it left open.** An approval still waiting when its run was deleted (by hand, by "clear runs", by the retention cleanup, or together with its workflow or its user) stayed in the assignee's pending list with nothing behind it. It is now closed as expired when the run goes.
- **A long task keeps your original request when you interrupt it more than once.** When the request and the interrupts sent mid-run together took more than half the context budget, compaction kept only the newest interrupt word for word and folded the original request into the summary. The original request and the newest interrupt are now both kept; only the interrupts in between are summarised.

- **More failures in the workflow editor give the server's reason.** Changing the status, exporting, deleting, publishing, unpublishing, resubmitting, validating and opening a workflow each showed one fixed sentence whatever the server answered. A refusal that comes with a reason now shows it; a failure without one, such as a dropped connection, keeps the fixed sentence. When your organisations cannot be loaded, the Publish dialog says so instead of stating that there is none to publish to.
- **Workflow run results name their steps.** The run panel, the run history, Node Stats and Analytics listed steps by internal id (`llm_1731…`) and the run panel never showed its progress. They now show the step type next to the id, and the run panel shows how many steps have finished out of the total.
- **The workflow editor no longer reloads itself while you work.** The editor fetched the workflow again whenever your session was refreshed (about every two hours) or your profile was updated: the canvas was rebuilt, undo history and the open settings panel were lost, and so was any edit from the last few seconds. Opening a workflow also loaded it twice. It is now loaded once.
- **A restored workflow version is not overwritten by a save that was already on its way.** Restoring a version within five seconds of an edit, or while a save was in progress, could end with the canvas showing the restored version, the toolbar saying "Saved" and the server holding the version from before the restore. The editor now stops saving before it asks for the restore and resumes once the restored version is loaded.
- **Restoring a workflow version, and Import inside the editor, change the canvas.** Both changed the workflow behind the editor and left the canvas showing the previous graph: a restored version was replaced by the old graph again a few seconds after the next click on the canvas, and an imported file was reported as imported while nothing changed. The canvas now shows the restored or imported workflow. A file that is not a workflow export is refused with a message instead of being ignored. Because an import replaces everything on the canvas, the editor asks for confirmation first when the canvas has steps or unsaved edits.
- **Leaving the workflow editor with unsaved changes asks first.** "Back to Workflows" or a sidebar link left the editor at once, and edits from the last five seconds were lost. With unsaved changes the editor now asks whether to stay or to discard them and leave.
- **Renaming a workflow is saved, and is no longer undone by the automatic save.** A new name, description or icon marked the workflow unsaved but was only sent with the next manual save, and a rename made within five seconds after moving a step was replaced by the old name when the automatic save ran. They now save themselves after the same five-second pause as any other edit.
- **An edit made while a save is in progress is not reported as saved.** The editor showed "Saved" for whatever was on the canvas when the server answered, including edits made after the request had left, and those were not sent until the next edit. Such an edit now stays marked unsaved and is saved after the usual pause. Duplicate saves unsaved edits before it copies.
- **Saving a workflow includes the edit you just made.** Save, Cmd+S and the automatic save sent the canvas as it was up to 0.3 seconds earlier, so a connection drawn or a field typed immediately before saving was left out until the next save.
- **Workflow variables are no longer dropped when the canvas changes.** Variables defined in the editor's Variables panel were removed from the workflow the next time a step was moved, selected or edited, and a workflow that already had variables was marked unsaved on opening and lost them at the next automatic save. They now stay until they are removed in the Variables panel.
- **A Connector step in a workflow can be pointed at a connector.** The step's two dropdowns held nothing but their placeholder, so a connector and an action could not be chosen in the editor. They now list your connectors and the actions of the chosen one; choosing another connector clears the action. Disabled connectors are not listed, since a Connector step cannot run them, and neither is a database connector that belongs to someone else.
- **Long conversations stay within the context window whatever models an agent mixes.** The chat context budget now comes from the models a turn runs on (the agent's own model and fast model, or the active model group) instead of the system default model, and the conversation is kept within the smaller of the two windows, since both models read it. When the history to condense is larger than the fast model's window, it is summarised in consecutive parts; it used to go out as one oversized request that the provider rejected, after which older turns were dropped without a summary. A model with no context size configured is budgeted as the system model for its role (`LLM_CONTEXT_SIZE`, 128,000 by default). `CONTEXT_GUARD_MAX_COMPACT_CHUNKS` (default 8) caps the summary requests per compaction.
- **A shared connector that takes no credential is no longer hidden by the fallback switch.** A connector whose authentication is "None" has nothing of the owner's to lend. With "allow fallback" off, it was still left out for everyone but its owner, unless they saved a credential the connector does not use. It is now offered to everyone who can use it: subscribers, and users of an agent that binds it. MCP servers are unchanged: with fallback off, anyone but the owner connects with a credential of their own or not at all, whatever the server stores, because a server's URL and command arguments are the owner's as well.
- **A conversation or connector that has call records can be deleted.** Deleting a conversation in which a connector had been called (one by one, in bulk, or by an administrator), or deleting a connector that had been called, failed with a server error: its call records still pointed at it and blocked the delete. Deleting an account failed the same way when another user had called one of its connectors. The delete now goes through and the call records stay as they were, still naming the conversation and the connector, so the history of what was called is kept. Deleting an account still removes that account's own call records.
- **A connector call with a long action description is recorded on PostgreSQL.** The record stored the action's description, and PostgreSQL rejected one longer than 200 characters, so the call left no record at all. The text is now shortened to fit.
- **Binding a knowledge base that is not yours to an agent is refused when you save.** Knowledge bases cannot be shared, and an agent already ignored a bound knowledge base its owner does not own. Saving such a binding was still accepted where an old subscription to the knowledge base was left over, so the agent looked configured and never used it. The save now answers `kb_ownership_denied`.
- **A knowledge base you switched off is no longer searched from chat.** In a conversation with no agent, or with an agent that has no knowledge base bound, the assistant can search one of your knowledge bases by its id. That search skipped the on/off switch, so a knowledge base you had switched off was still read. The assistant is now told the knowledge base is not available. Knowledge bases bound to an agent already followed the switch.
- **Admin → Sessions lists the sessions that have not expired, whatever the server's time zone.** On PostgreSQL the cut-off was off by the API server's UTC offset: on a server ahead of UTC, sessions that had expired within the last few hours were still listed, and behind UTC, sessions about to expire were left out. A server running in UTC was not affected.
- **Workflow errors say what went wrong.** When the server refuses to save a workflow because a setting is invalid, the editor now names each step and field at fault, in the notice and as a badge on the step, also when the save was automatic. A manual save used to show only "Failed to save workflow" and an automatic one showed nothing, so the edits were lost without a word. Refusals to import, duplicate, restore, run, batch-run or test a workflow (too many runs, already running, switched off, owner's account disabled and others) now show their reason instead of a generic failure.
- **An error without a translated message shows the server's text.** Across the app such an error was shown as an internal key such as `errors.some_code`.
- **A workflow dry run no longer reports "valid" for a workflow that would be refused.** `POST /api/workflows/{id}/run` with `dry_run` only checked the workflow's structure. It now also answers what a real run by the caller would be refused for (account or workflow owner disabled, token quota, plan, a switched-off Human Intervention step): `valid` is `false`, `errors` gives the reason and the new `error_code` field carries the code the run would return. A dry run still starts nothing and uses no rate-limit budget, so it does not predict the concurrent-run and runs-per-minute limits.
- **A workflow trigger key starts one run at a time, also when requests arrive together.** Trigger requests that arrived at the same moment could each start a run of the same workflow. Exactly one now runs and the others get `429 workflow_already_running`.

When an approval times out it is now marked expired instead of staying pending.

- **Every tool in a conversation now works on one shared filesystem.** Offloaded large outputs used to land in a directory only the workspace-reading tools could see, while `file_ops`, `shell_exec` and `python_exec` operated elsewhere — the agent would list a file, then be told it doesn't exist, and burn its iteration budget hunting for it. Offloaded files now live in the conversation sandbox that every tool (including exec containers) mounts; files from older conversations remain readable.

Workspace reads are now clamped with an exact resume line instead of being re-offloaded.

The truncation is now detected, and the agent is told to retry with the work split into smaller calls.

Fully addressed? ✅ …" instead of the answer itself. The check is now internal, and the reply you see is written as its own step.

- **Refresh-token rotation now actually invalidates the previous token.** JWT `exp` is only second-precision, so two refresh tokens issued for the same user in the same second used to encode identically — rotation then rewrote the stored hash with the same value, and a stolen refresh token could be renewed forever. Each refresh token now carries a unique `jti`, so the rotated token differs and the old one stops working immediately.

- **Approval gates now hold when an agent is reached through another agent or a workflow.** A sensitive connector call that would ask for confirmation in chat previously ran unchecked once it was delegated via `call_agent` or wrapped in a workflow `AGENT` node — those paths started the agent with no hooks at all. Both now run the agent's own gates, using that agent's confirmation settings, and refuse to run it if its hooks can't be loaded.

- **A typo in `SMTP_SSL` no longer silently sends your SMTP password in cleartext.** Previously any value other than `ssl` or `tls` (for example `SMTP_SSL=true`) fell through to an unencrypted connection without warning, in both system emails and email notifications. Unrecognized values are now rejected outright, and unencrypted delivery must be requested explicitly as `SMTP_SSL=none`, which logs a warning on every send.

### Added

- **Skills and Workflows are now optional modules, off by default.** A new install boots with just the core (chat, agents, knowledge bases, connectors); an admin turns Skills and/or Workflows on from Admin → Settings → Modules. Each such run is recorded in the workflow's run history and its token usage counts against the workflow owner's quota (the run is refused if the owner is already over quota). - **API-key scopes are now carried per-request instead of being attached to the user object.** This closes a latent scope-confusion path where a cached or identity-map-shared user could inherit another auth context's scope set.

### Fixed

- **OAuth sign-in now fails fast with a clear "provider took too long" message when GitHub/Google/Discord/Feishu are slow**, instead of hanging on library-default timeouts and surfacing a generic failure.
- **Agent no longer generates a spurious image when asked to restyle an HTML deliverable, and never claims a file was created without actually writing it to the workspace.** Image generation is now explicitly scoped to raster pictures, and file deliverables must be written via a tool call — pasting content in chat no longer passes as "generating a file".
- **Generated HTML pages now default to a warm Claude-inspired palette instead of the generic purple-gradient look.** When you don't specify a style, the agent uses a warm minimal baseline; your own style always wins when specified.
- **Long tool-heavy conversations no longer break when history is compacted.** Context compaction could cut the kept window between a tool call and its results, producing a message sequence the LLM provider rejects outright (HTTP 400) — exactly on the long runs that need compaction most. The compactor now keeps each tool call together with its results on the kept side.
- **Background tool results now show up in the step stream and in DAG evidence.** A tool run in the background used to deliver its real output only inside the agent's internal notification message — the UI's step timeline and the DAG answer-verification evidence saw nothing but the dispatch placeholder. The drained result is now emitted as a normal tool completion event under the real tool name.
- **A rare planner output with duplicate step ids no longer fails the whole DAG turn.** Duplicate ids used to be misdiagnosed as a "circular dependency" error; they are now renamed deterministically and the plan proceeds.
- **Several ReAct loop correctness fixes.** A tool returning empty output kept its "completed with no output" note instead of a blank result when the workspace is enabled; DAG steps blocked by an unsatisfiable dependency now emit a proper terminal event instead of leaving the UI hanging; and for models without native tool calling, the fallback answer synthesis now sees the tool results, not just the tool calls.
- **The conversation workspace is now actually wired into chat — oversized tool results are recoverable instead of silently lost.** The agent layer's workspace recovery paths (large-output offload with a `workspace://` pointer, full-copy rescue of budget-truncated tool results, pre-compaction transcript snapshots) existed but the chat endpoints never created a workspace, so none of them ran: once the tool-result budget was exhausted the model received empty observations with no way to read the data back, and answered from guesswork. ReAct and DAG-step agents now get a per-conversation workspace, and deleting a conversation cleans up its workspace files and any leftover crash-resume checkpoint.
- **Resumed DAG runs no longer lose the end of long step outputs.** Step evidence stored in the crash-resume checkpoint was cut head-only at the size cap, silently dropping whatever lived at the end of the output — which is exactly where conclusions, checksums, and final rows tend to be. Capped evidence now keeps both the head and the tail with an explicit omission marker in between.
- **Agents no longer "work" by printing their own notes through Python.** The efficiency guidance that encouraged writing one comprehensive script per tool call is now scoped to tasks that genuinely need code execution — knowledge questions, comparisons, and analysis the model can produce directly are answered directly instead of being routed through pointless sandbox scripts.
- **An agent step inside a workflow now runs the full agent, not just its prompt.** A workflow's Agent node used to execute with only the agent's instructions on a generic model and default toolset — silently dropping the agent's connectors, knowledge bases, MCP servers, and configured model. It now runs the agent exactly as it would in chat, with all of its bound resources and model, and only if that agent is visible to the workflow owner.
- **Leaving (or being removed from) an organization now revokes its shared access.** Resources you could reach only through that organization are unsubscribed, and the per-user connector/MCP credentials you saved for them are deleted — so you can no longer use those resources or fall back to the owner's credential after departing. Resources you subscribed to via the Market are unaffected.
- **Deleting an account now removes everything, consistently.** The admin "delete user" and self-serve "delete my account" paths used to diverge — each cleaned a different set of on-disk files (and both computed their file paths wrongly, so each silently missed some), and the admin path left behind API keys, login history, eval data, call logs, and subscriptions. Both now run through one routine that removes every record and file, and the delete no longer fails on databases that enforce foreign keys.
- **A user who still owns an organization can no longer be deleted.** The request is now rejected with a clear message to transfer ownership (or delete the organization) first, instead of failing obscurely or leaving the organization orphaned.
- **Deleting an agent no longer breaks past conversations.** Conversations that referenced the agent are kept as historical records and simply have the agent link cleared, rather than blocking the deletion.
- **Confirmation-required connector actions can no longer run unattended in a workflow.** A connector action flagged as requiring confirmation used to execute inside a workflow with the approval gate silently bypassed. The step now fails closed with a message to place a Human Intervention node before it (the workflow-native approval gate) or use an action that doesn't require confirmation.
- **Workflow steps no longer borrow the owner's MCP credentials.** When a workflow's MCP server had owner-credential fallback disabled, a non-owner running that workflow silently fell back to the owner's server credentials instead of being stopped. The step now fails with a clear message to configure your own credentials, matching the chat path.
- **Connector calls made from workflows are now audit-logged.** A connector action run inside a workflow left no entry in the connector call log (only chat-initiated calls were recorded); workflow calls now write the same audit trail.
- **You can now attach a subscribed connector, knowledge base, or MCP server to an agent.** Binding used to require you to *own* the resource, so a connector you'd legitimately subscribed to (org-shared or Market-installed) was rejected as "not owned". Binding now follows the same visibility rule the rest of the app uses — anything you own or have subscribed to is bindable.
- **Workflow steps can only call connectors you actually have access to.** A workflow's connector step used to run any connector whose id it referenced, as long as that connector existed; it now enforces the runner's visibility (owned or subscribed), so a shared workflow can't reach a connector you have no access to just by referencing its id.
- **Knowledge base search now works against KBs you subscribed to, not just ones you own.** A KB's data lives under its owner's storage, but a workflow knowledge-base step (and knowledge-base chat without an agent) used to look under the caller's own storage — so searching a KB shared with you silently returned nothing. The owner is now resolved from the KB itself and the search is access-checked (owner or subscriber), so shared KBs return results and KBs you can't see return nothing instead of a confusing empty hit.
- **Background jobs no longer vanish at random.** Document ingestion, webhook delivery, eval runs, and post-response notifications were launched as fire-and-forget tasks the runtime only weakly referenced, so under load they could be garbage-collected mid-flight and stop silently. They are now held until completion (and their failures logged) so they reliably finish.
- **Large file uploads no longer stall other requests.** Text extraction from an uploaded PDF/DOCX ran synchronously on the main event loop, briefly freezing all concurrent requests while a big file was parsed. Extraction is now offloaded to a worker thread.
- **Multi-step (DAG) answers no longer misrepresent their sources.** When a plan's research step fetched a page and summarized it, only that summary flowed onward — so a source that listed 11 items could surface in the final answer as 6, or an item's severity could be mislabeled, and the goal-evaluation step couldn't catch it because it never saw the original source. Each step now retains its raw tool output as authoritative source evidence, which the final synthesis and the evaluator check the answer against, so totals, enumerations, and attributes match what the sources actually said (and confidence drops with a named discrepancy when they don't).
- **The workflow LLM node no longer shows model controls that didn't mean what they implied.** It had a hardcoded model dropdown whose selection was ignored at run time, plus a Fast/Main tier toggle exposing an internal (auto-degrading) concept. Both are removed — the node now always runs your system-configured model (Model Provider, falling back to `.env`), the same way the playground resolves it, with a one-line note pointing to where the model is configured.
- **The agent editor no longer warns about unsaved changes when nothing was edited, and saving no longer fails with an approver-scope error.** Opening an agent and leaving could trigger a phantom "unsaved changes" dialog, and saving an agent with a legacy approver-scope value could be rejected outright — both traced to the same field being read inconsistently. The editor now normalizes those fields on load, so the dirty check is accurate and a stale stored value is corrected instead of echoed back.

## [v0.8.8] - 2026-06-22

### Changed

- **Agents now own mistakes more cleanly.** When a tool result contradicts something an agent said, it acknowledges and corrects in the same turn without over-apologizing or padding the reply with self-criticism.

### Security

- **Blocked an SSRF bypass via IPv4-mapped IPv6 addresses.** A URL whose host was an IPv4-mapped IPv6 literal (e.g. `http://[::ffff:169.254.169.254]/`) slipped past the private-IP blocklist and could reach internal services — including cloud instance-metadata — on dual-stack hosts. These addresses are now unwrapped and checked against the IPv4 blocklist, closing the gap across every SSRF-protected path (web fetch, HTTP tool, connectors, RAG importer).
- **MCP SSE / Streamable-HTTP server URLs are now SSRF-validated.** An authenticated user could point an MCP server at an internal address and trigger a request to it when the server was tested or connected. Server URLs are now validated on create/update and again at connect time.
- **Docker Compose PostgreSQL credentials are now overridable via `POSTGRES_USER` / `POSTGRES_PASSWORD` / `POSTGRES_DB`.** The previously hardcoded `fim:fim` default is single-sourced (the connection string is derived from the same vars) and documented with a warning to change it before exposing the database, so operators no longer ship default admin credentials by accident.

### Fixed

- **LLM access no longer dies after a quiet period.** The shared HTTP connection pool was installed once at startup and reused for every model call; after the system sat idle, the underlying client could be closed out from under the app, after which every LLM call failed with a connection error until the service was restarted. The pool is now re-validated and transparently recreated before each call, so service recovers on its own without a restart.
- **Sending a message in a chat now streams instantly instead of stalling.** Each send used to block on a full reload of the conversation's history before the answer could start, so longer chats felt frozen for a moment and refetched the entire transcript every turn. A completed turn is now folded into history in the background, so sends stream immediately and skip the redundant reload.
- **Extended thinking now works on newer Anthropic models (Opus 4.6+, Sonnet 4.6, Fable 5).** These models removed the old fixed-budget thinking parameter — Opus 4.7/4.8 and Fable 5 reject it with a 400 — so configuring reasoning effort either errored or silently did nothing. We now send the adaptive-thinking protocol for these models (and drop the sampling parameters they no longer accept), so reasoning effort takes effect correctly. A model that uses adaptive thinking but is connected through a generic OpenAI-compatible proxy (where thinking can't be enabled) now logs a clear warning instead of failing silently — configure it as an Anthropic provider to enable thinking.
- **Force-logout now compares timestamps correctly on PostgreSQL.** The session-invalidation check assumed the stored invalidation time was naive UTC and forced it as such, which silently corrupted comparisons against tz-aware non-UTC values that PostgreSQL can return. Timestamps are now normalized to UTC by conversion, not override, so revoked tokens are reliably rejected on every backend.
- **Enforcement hooks now fail closed when they crash.** A `PRE_TOOL_USE` hook (e.g. an approval gate) that raised an exception previously returned `allow=True`, so the blocked tool call proceeded anyway — a crashing gate silently became a bypass. PRE hooks now deny by default on error; non-enforcement hooks (rate limiter, loggers) keep the old fail-open behavior via a new `fail_open` flag.
- **Agent answers no longer drop the reasoning's conclusions.** When a reasoning model had already produced a final answer, the pipeline made a second, lossy synthesis call that could discard the model's own conclusions — and reasoning detail was further lost when conversations were compacted, guarded against the context limit, or routed through multi-step plans. The loop now streams its genuine final answer verbatim, and reasoning is carried through compaction, context rebuilds, and sub-agent steps, so the answer you see reflects the full chain of thought instead of a watered-down restatement.

### Security

- **Token quota now resets on your billing date, not the 1st of the month.** Usage was always counted per calendar month regardless of when you subscribed, so paid users could be charged on the 20th yet wait until the 1st for a fresh quota — and a subscription started late in the month effectively granted a second full quota days later.
