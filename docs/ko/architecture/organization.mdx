## Overview

Organizations are FIM One's unit for team collaboration. They let groups of users share resources — Agents, API Connectors, and MCP Servers, plus Skills and Workflows when an administrator has enabled those modules — within a trusted scope. Knowledge Bases and database connectors are the exceptions: database connectors cannot be published, and Knowledge Bases are never shareable, and reach other members only as an internal dependency of a shared Agent (see [Sharing and credentials](/architecture/sharing-and-credentials)).

Every resource in FIM One starts as **personal** (visible only to its creator). When you publish a resource to an organization, it becomes **discoverable** by other org members through the Market's organization scope. Members browse the org's shared resources and subscribe to the ones they need.

```mermaid
flowchart TD
    R["Personal Resource"]

    subgraph OrgPublish["Organization"]
        O["Org Scope in Market"]
        M1["Member A<br/>(subscribes)"]
        M2["Member B<br/>(subscribes)"]
        M3["Member C<br/>(browses only)"]
    end

    R -->|"publish to org"| O
    O -->|"subscribe"| M1
    O -->|"subscribe"| M2
    O -.->|"visible but not subscribed"| M3
```

Organizations and the global Market share the same subscription-based access model. The key difference is trust: organizations represent a team or company where members know and trust each other, so review is optional and credential sharing is straightforward.

## 조직 생성 및 관리

모든 사용자는 **무제한** 조직을 생성하고 여러 조직에 참여할 수 있습니다. 조직에는 세 가지 역할이 있습니다:

| 역할 | 권한 |
|---|---|
| **소유자** | 완전한 제어 — 멤버 관리, 설정 구성, 검토 우회 |
| **관리자** | 멤버 관리 및 게시된 리소스 검토 |
| **멤버** | 공유된 리소스 검색 및 구독 |

소유자는 항상 조직을 생성한 사용자입니다. 소유권은 이전할 수 있지만 공유할 수는 없습니다.

## 리소스 게시

조직에 리소스를 게시하면 조직의 모든 멤버 워크스페이스에 **자동으로** 나타나지 않습니다. 대신, 리소스는 마켓의 조직 범위에서 검색 가능해지며, 멤버들은 여기서 리소스를 찾아보고 구독할 수 있습니다.

이 구독 기반 모델은 각 멤버에게 자신의 워크스페이스에 대한 제어권을 제공합니다. 대규모 조직은 수십 개의 커넥터를 공유할 수 있지만, 개별 멤버는 자신의 업무와 관련된 것들만 구독합니다.

```mermaid
sequenceDiagram
    participant U as Publisher
    participant P as Platform
    participant O as Org Settings
    participant M as Other Members

    U->>P: Publish Agent to Org
    P->>O: Check review_agents flag
    alt Review disabled
        P->>P: publish_status = NULL (auto-approved)
        P-->>U: Resource discoverable by org members
    else Review enabled
        P->>P: publish_status = "pending_review"
        P-->>U: Pending admin approval
        Note over P: Org admin approves or rejects
        P->>P: publish_status = "approved"
    end
    M->>P: Browse org resources in Market
    M->>P: Subscribe to Agent
    P-->>M: Agent appears in workspace
```

### Review System

Review is **optional** and configured per resource type. Each organization has independent toggle flags:

- `review_agents`
- `review_connectors`
- `review_mcp_servers`
- `review_workflows`
- `review_skills`

When review is disabled for a resource type, published resources are immediately discoverable by members — no admin action needed. When review is enabled, resources enter a `pending_review` state and require admin approval before they become visible.

<Tip>
Organization owners bypass review automatically. Their published resources are always immediately discoverable.
</Tip>

This flexibility lets organizations match their governance needs. A small startup might disable all review toggles for frictionless sharing, while a compliance-focused enterprise enables review on Agents and Connectors to maintain oversight.

## Credential Fallback

Connectors and MCP Servers often require credentials (API keys, database passwords, OAuth tokens). FIM One provides a **fallback mechanism** so that members don't have to configure every credential themselves.

```mermaid
flowchart TD
    E["Member uses a shared Connector"]
    C1{"Member has own credential?"}
    C2{"allow_fallback enabled?"}
    C3{"Owner set default credential?"}

    E --> C1
    C1 -->|Yes| U["Use member's credential"]
    C1 -->|No| C2
    C2 -->|Yes| C3
    C3 -->|Yes| F["Fallback to owner's default"]
    C3 -->|No| ERR["Error: credential required"]
    C2 -->|No| ERR2["Error: credential required"]
```

There are two modes:

- **Fallback disabled** (`allow_fallback=false`, the default): Every member must configure their own credentials; until they do, the tool is hidden from their agents. This is appropriate when each user needs a personal API key (for example, per-seat SaaS licenses).
- **Fallback enabled** (`allow_fallback=true`, set by the owner): Members who don't provide their own credentials automatically use the owner's default credentials. This works well for team-shared API keys or internal services where a single key covers the whole team.

Resources that don't require credentials — such as a read-only public API connector or an Agent with no authentication — work immediately after subscription. No configuration needed.

### MCP servers: the address is the owner's

A member's own credential for an MCP server is a set of environment variables (stdio servers) or request headers (SSE and HTTP servers). The server's URL and its launch arguments have no per-member counterpart: whoever connects, connects to what the owner configured. If the owner put a credential there, a member's own credential does not replace it.

So with fallback disabled, an MCP server whose address looks like it carries a credential can be used by its owner only. Other members are refused with `mcp_server_address_private`, whether or not they saved credentials of their own, and the server's card tells them so instead of asking for keys. The owner sees a warning on the card and in the editor once the server is shared, or once one of the owner's shared agents or workflows uses it (the people who run those are refused the server the same way) (the save and publish responses carry `warning: "mcp_server_address_private"` and, in `warning_reasons`, which part of the address counted: the query string, the user-info, a path segment, an argument name and so on, never the value), and has two ways out:

- move the credential into a header or an environment variable, so that each member brings their own; or
- enable fallback, which lends the server as configured: the address, and with it the headers and environment variables saved on the server. Members without credentials of their own then act under the owner's.

What counts as "carries a credential" is decided by shape:

| Where | Counts | Example |
| --- | --- | --- |
| URL | user-info, any query string, a fragment | `https://user:pass@host/mcp`, `https://host/mcp?token=…` |
| URL | a path segment shaped like a token: a UUID, 16 or more hex digits, 20 or more characters mixing letters and digits, or a known token prefix; a `;name=value` path parameter | `https://mcp.zapier.com/api/mcp/s/<secret>/mcp`, `https://host/<32 hex>/sse`, `https://host/mcp;token=…` |
| Launch arguments | a flag, assignment or header with `token`, `key`, `secret`, `password`, `passwd`, `pwd`, `auth`, `authorization`, `credential(s)`, `bearer`, `pat`, `dsn`, `connection`, `cookie` or `session` as a whole word of its name, given a value | `--api-key VALUE`, `--token=VALUE`, `API_KEY=VALUE`, `apiKey=VALUE`, `X-Api-Key: VALUE` |
| Launch arguments | a URL that counts by the URL rows above | `--endpoint=https://host/?key=…`, `mcp-remote https://host/<32 hex>/sse` |
| Launch arguments | a known token shape | `sk-…`, `ghp_…`, `gho_…`, `github_pat_…`, `xoxb-…`, `xoxp-…`, `AKIA…`, `glpat-…`, `ntn_…`, `hf_…`, `AIza…`, a JWT, `Bearer <token>`; any UUID or value of 32 or more characters mixing letters and digits |
| Launch arguments | Docker's `-e NAME=VALUE` / `--env NAME=VALUE`, whatever the name | `docker run -e NOTION_API=…` (`-e NAME` alone passes the variable through and does not count) |
| Launch arguments | a connection string with `Password=` / `Pwd=`, or a DSN starting `user:pass@` | `Server=db;Password=…`, `user:pass@tcp(db:3306)/app` |

Names are read word by word (split at `-`, `_`, `.` and camelCase), so `--keyboard-layout`, `--tokenizer`, `--author` and `--hotkey` do not count; neither do plurals (`--max-tokens 100`), a name that negates (`--no-auth true`), a name that describes where or how (`--key-file /path`, `--auth-type basic`), or a switch for a value (`--auth none`). Any query string counts, `?v=2` included: nothing tells a version from a token. The path rule is a heuristic, which is why the warning says the address *may* contain a credential: an opaque id in the path that is no secret counts, and a short or worded secret segment (`https://host/mcp/hunter2/sse`) does not. The fixed addresses of the well-known remote servers (GitHub, Linear, Notion, Sentry, Atlassian, Context7, Cloudflare, Asana, Hugging Face) are not flagged. The check also does not recognise a short secret passed as a bare positional argument or after a flag whose name says nothing (`-k hunter2`, `--id abc123`); a long opaque one is recognised wherever it stands. Keep credentials in headers and environment variables, where they are encrypted at rest and never shown to other members.

Other members never see a shared server's URL, command or launch arguments, with fallback on or off.

### Agents with a custom model endpoint are the owner's

An agent normally selects a model an administrator configured under Admin → Models. Its inline model settings (`model_config_json`, set through the API) may instead name an endpoint of their own: a `base_url` with the `api_key` that goes with it. Every turn of a conversation with such an agent, the user's messages and files included, is sent to that address. Selecting a model configuration the agent's owner created with a `base_url` of its own (`model_config_id` or `fast_model_config_id`) counts the same. An agent uses only model configurations an administrator created or its owner created; one that names another user's configuration falls back to the default model.

By default such an agent is used by its owner only:

- it cannot be published or resubmitted for review, and a shared agent cannot be given a `base_url` (`agent_model_endpoint_not_shareable`, 400);
- an agent that was shared before it had to follow this rule stays published, but everyone except its owner is refused with `agent_model_endpoint_private` (403), in chat, when another agent delegates to it and in a workflow Agent step, and it is not offered for delegation. Its owner can remove the `base_url` and select a configured model, which makes it usable by subscribers again.

A platform administrator who accepts that members' conversations go to the endpoints authors choose sets `shared_custom_model_endpoints` to `true` with `PATCH /api/admin/settings`; publishing such agents is then allowed and subscribers use them as before. The setting is off unless it has been set.

<Info>
Credential fallback only applies after a member subscribes to the resource. The fallback mechanism determines how credentials are resolved at runtime, not whether the resource is accessible.
</Info>

## 리소스 가시성

FIM One의 모든 리소스에는 접근 범위를 결정하는 `visibility`가 있습니다:

| 가시성 | 범위 | 발견 가능한 사용자 |
|---|---|---|
| `personal` | 소유자만 | 리소스를 생성한 사용자 |
| `org` | 조직 | 조직 구성원은 검색 및 구독 가능 (승인 시) |

가시성 필터는 통합 쿼리 패턴을 따릅니다:

```
A resource is available in your workspace if:
  1. You own it (any visibility), OR
  2. It's published to an org you belong to, approved, AND you've subscribed to it
```

<Warning>
조직에 리소스를 게시해도 자동으로 접근 권한이 부여되지 않습니다. 구성원은 마켓의 조직 범위를 통해 구독하여 리소스를 자신의 워크스페이스에 추가해야 합니다.
</Warning>

## Infrastructure Resources (org-wide, no subscription)

A second class of org-scoped resource does **not** follow the personal → publish → subscribe lifecycle above. These are **configured once by an Org Owner or Admin** and then transparently available to every agent in the org:

| Resource | Purpose | Configured by | Consumed by |
|---|---|---|---|
| **Channels** | Outbound bridge to an IM platform (Feishu today; Slack / WeCom / Teams planned) | Org Owner / Admin | Every agent's [Hook System](/architecture/hook-system) and proactive-notification tools |
| **OAuth Providers** | Social-login credentials (GitHub, Google, Feishu, Discord) | System admin (env vars) | Sign-in page |
| **API Keys** | Programmatic access tokens for headless clients | Each user, for their own account | External integrations |

```mermaid
flowchart LR
    Admin["Org Owner / Admin"]
    subgraph Org["Organization"]
        Ch["Channel<br/>(e.g. FIM One ↔ Feishu group)"]
        A1["Agent A"]
        A2["Agent B"]
        A3["Agent C"]
    end
    Admin -->|"configure once"| Ch
    A1 -. "uses via approval_gate hook" .-> Ch
    A2 -. "uses for notifications" .-> Ch
    A3 -. "uses for approval cards" .-> Ch
```

The key distinction: **publishable resources** (Agents, Connectors, Skills, …) are per-user artifacts that need explicit member subscription; **infrastructure resources** (Channels, OAuth, API keys) are platform-level wiring that all agents share implicitly. Channels specifically are the IM hotline for the whole org — one well-maintained Feishu channel backs every agent's approval gate, every scheduled report, every escalation event.

See [Channels overview](/configuration/channels/overview) for the channel lifecycle and supported platforms.

## 실제 시나리오

### Team Sharing an API Connector

1. Alice creates a Connector to the team's internal order API and turns on **Allow fallback**
2. Alice publishes it to her team's org (review is disabled for connectors)
3. The Connector becomes discoverable in the org scope of the Market
4. Bob browses the org's shared resources, finds the Connector, and subscribes
5. The Connector appears in Bob's workspace, using Alice's API credentials as fallback
6. Carol subscribes too. Dave (an external contractor) subscribes and configures his own read-only credentials instead

Database connectors cannot be published to an organization or the Market; each user who needs one creates their own.

### 엄격한 검토를 통한 조직 관리

1. 규정 준수에 중점을 두는 회사가 조직에서 `review_agents=true` 및 `review_connectors=true`를 활성화합니다
2. 직원이 새로운 에이전트를 게시하면 `pending_review` 상태로 진입합니다
3. 조직 관리자가 에이전트 구성을 검토하고 승인합니다
4. 에이전트가 검색 가능해지며 — 다른 멤버들이 이제 에이전트를 찾고 구독할 수 있습니다
5. 게시자가 나중에 승인된 에이전트를 편집하면 재승인을 위해 자동으로 `pending_review`로 되돌아갑니다

### Selective Subscription in a Large Organization

1. An organization publishes 50+ Connectors covering internal APIs and third-party services
2. The data team subscribes only to the data-warehouse and analytics API Connectors
3. The marketing team subscribes only to the CRM and email platform Connectors
4. Each team member's workspace stays focused and uncluttered
