## Aperçu

L'API FIM One prend en charge deux méthodes d'authentification :

1. **Clés API** — Jetons simples et durables pour l'intégration de service à service
2. **Jetons JWT** — Jetons de courte durée issus de la connexion utilisateur (pour les points de terminaison SSE)

La plupart des intégrations doivent utiliser les **Clés API**.

## Clés API

Les clés API sont des identifiants de longue durée liés à votre compte utilisateur. Elles sont idéales pour :

- Les intégrations serveur à serveur
- Les scripts planifiés et l'automatisation
- Les applications externes accédant à FIM One

### Création d'une clé API

1. Connectez-vous à votre portail FIM One
2. Allez à **Paramètres → Clés API**
3. Cliquez sur **Créer une clé API**
4. Entrez un nom (par exemple, « Intégration Production »)
5. (Facultatif) Définissez les portées pour limiter l'accès
6. (Facultatif) Définissez une date d'expiration
7. Cliquez sur **Créer**
8. Copiez la clé immédiatement — elle n'est affichée qu'une seule fois

La clé complète ressemble à : `fim_your44characterkeystringhere` (commence par le préfixe `fim_`)

### Utilisation des clés API

Incluez la clé dans l'en-tête `Authorization` en tant que jeton Bearer :

```bash
curl -H "Authorization: Bearer fim_your_api_key_here" \
  https://your-domain.com/api/conversations
```

Ou en Python :

```python
import requests

headers = {
    "Authorization": "Bearer fim_your_api_key_here"
}

response = requests.get(
    "https://your-domain.com/api/conversations",
    headers=headers
)
print(response.json())
```

### Fonctionnalités des clés API

**Visibilité** : Chaque clé affiche :
- Préfixe de clé (premiers 8 caractères pour l'identification)
- Date de création
- Horodatage de la dernière utilisation
- Nombre total de requêtes
- Statut actif
- Date d'expiration (si définie)

**Gestion** : Vous pouvez :
- Activer/désactiver les clés sans les supprimer
- Définir des dates d'expiration automatiques
- Supprimer les clés de manière permanente
- Suivre les modèles d'utilisation

### Portées

Les portées limitent ce qu'une clé API peut accéder. Si aucune portée n'est définie, la clé a un accès complet.

Une clé avec des portées ne peut appeler que les points de terminaison que ses portées autorisent. Tous les autres points de terminaison répondent `403`, y compris la gestion des clés API sous `/api/me/api-keys`, qui nécessite une clé sans portées ou une session connectée. Une clé ne peut jamais créer une clé avec des portées plus larges que les siennes.

Portées disponibles :

| Portée | Autorise |
|--------|----------|
| `chat` | POST /api/react, POST /api/dag, POST /api/auto, POST /api/chat/ticket, POST /api/chat/inject, POST /api/chat/inject/recall, POST /api/chat/resume, et GET/POST /api/conversations, GET/PATCH/DELETE /api/conversations/`{id}` |
| `agents` | GET /api/agents, GET /api/agents/`{id}` |
| `kb` | GET /api/knowledge-bases, POST /api/knowledge-bases/`{id}`/retrieve |
| `connectors` | Tout sous /api/connectors |
| `admin` | Tout sous /api/admin (le propriétaire de la clé doit être un administrateur) |

Créer une clé avec des portées :

```bash
curl -X POST https://your-domain.com/api/me/api-keys \
  -H "Authorization: Bearer your_current_api_key_or_jwt" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Chat-only Integration",
    "scopes": "chat"
  }'
```

## JWT Tokens

JWT tokens are short-lived and issued at login. They're used for:

- **SSE Streaming Endpoints**: Pass tokens in the request body for `/api/react`, `/api/dag` and `/api/auto`
- **Portal Session**: Frontend authentication

### Obtenir un jeton JWT

Les jetons JWT sont automatiquement émis lorsque vous vous connectez via le portail web ou appelez le point de terminaison d'authentification :

```bash
curl -X POST https://your-domain.com/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{
    "email": "user@example.com",
    "password": "your_password"
  }'
```

Réponse :

```json
{
  "access_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
  "refresh_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
  "token_type": "bearer",
  "expires_in": 7200,
  "user": { ... }
}
```

### Two-factor authentication

When the account has two-factor authentication enabled, sign-in does not return tokens. `POST /api/auth/login` and `POST /api/auth/login-with-code` answer with a short-lived temporary token instead:

```json
{
  "requires_2fa": true,
  "temp_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9..."
}
```

Send it with the TOTP code (or a backup code) to finish signing in. The response is the same token payload as a normal login:

```bash
curl -X POST https://your-domain.com/api/auth/login/verify-2fa \
  -H "Content-Type: application/json" \
  -d '{
    "temp_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
    "code": "123456"
  }'
```

The temporary token is valid for 5 minutes. Signing in through an OAuth provider (GitHub, Google, Discord, Feishu) stops at the same step: the callback hands the browser a 2FA challenge instead of tokens. After 5 incorrect codes within 15 minutes for the same account, the endpoint answers `429` with `error_code` `2fa_too_many_attempts`; starting a new sign-in does not reset the count.

### Using JWT for Streaming

For SSE endpoints, include the token in the request body. The field accepts a JWT access token or an API key (a scoped key needs the `chat` scope):

```bash
curl -X POST https://your-domain.com/api/react \
  -H "Content-Type: application/json" \
  -d '{
    "q": "What are the top 3 Python frameworks?",
    "token": "your_jwt_token_here"
  }'
```

Or from JavaScript using `fetch` with a readable stream (the endpoint is POST-only, so native `EventSource` which only supports GET cannot be used):

```javascript
const response = await fetch("https://your-domain.com/api/react", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({
    q: "Hello",
    token: "fim_your_api_key_here"
  })
});

const reader = response.body.getReader();
const decoder = new TextDecoder();

while (true) {
  const { done, value } = await reader.read();
  if (done) break;
  const chunk = decoder.decode(value);
  // Parse SSE events from chunk
  console.log(chunk);
}
```

### Actualisation du jeton

Les jetons d'accès expirent après 2 heures. Utilisez le jeton d'actualisation pour obtenir un nouveau jeton d'accès sans vous reconnecter :

```bash
curl -X POST https://your-domain.com/api/auth/refresh \
  -H "Content-Type: application/json" \
  -d '{
    "refresh_token": "your_refresh_token_here"
  }'
```

## Bonnes pratiques de sécurité

### Clés API

<Warning>
**Ne validez jamais les clés API dans le contrôle de version.** Elles fournissent un accès complet à vos données.
</Warning>

1. **Stockez dans des variables d'environnement** :
   ```bash
   export FIM_API_KEY="fim_your_api_key_here"
   ```
   Puis référencez dans le code :
   ```python
   api_key = os.environ.get("FIM_API_KEY")
   ```

2. **Utilisez la rotation des clés** :
   - Créez une nouvelle clé
   - Mettez à jour votre application
   - Supprimez l'ancienne clé
   - Répétez tous les trimestres

3. **Définissez des dates d'expiration** :
   - Utilisez des clés de courte durée pour les intégrations temporaires
   - Exigez une réauthentification périodique

4. **Utilisez des clés limitées** :
   - N'utilisez pas de clés « accès complet » sauf si nécessaire
   - Créez des clés séparées pour différents services
   - Limitez les dégâts si une clé est compromise

5. **Surveillez l'utilisation** :
   - Vérifiez les horodatages « dernière utilisation »
   - Examinez les compteurs de requêtes
   - Supprimez les clés inutilisées

### Jetons JWT

1. **Garder une courte durée de vie** : Les jetons d'accès expirent après 2 heures
2. **Stockage sécurisé** :
   - Dans les navigateurs : utiliser les cookies HttpOnly (plus sûr que localStorage)
   - Sur les serveurs : utiliser le stockage de session sécurisé
3. **Ne jamais exposer dans les journaux** : Enregistrer uniquement le préfixe du jeton, pas le jeton complet
4. **Utiliser HTTPS uniquement** : Ne jamais envoyer les jetons sur des connexions non chiffrées

## Limites de débit

La limitation de débit par clé est prévue pour une version future. Actuellement, il n'y a pas de limites de requêtes appliquées par clé.

## Troubleshooting

Every error response has the shape `{"detail", "error_code", "error_args"}`. Errors raised while checking the `Authorization` header carry `error_code: null`; tell them apart by the status code and `detail`.

### Invalid Token Error

```json
{
  "detail": "Invalid token",
  "error_code": null,
  "error_args": {}
}
```

**Causes** (`401`; `detail` is `Invalid token`, `Invalid API key`, `API key is disabled` or `API key has expired`):
- API key prefix is wrong (must start with `fim_`)
- Token is malformed or corrupted
- API key has been deleted, disabled, or is past its expiration date

**Solution**: Verify your token format and re-generate if necessary

### Unauthorized Error

```json
{
  "detail": "Authentication required",
  "error_code": "authentication_required",
  "error_args": {}
}
```

**Causes** (`401`):
- Token is missing from the request body (SSE endpoints return the body above)
- No `Authorization` header provided (other endpoints answer `Not authenticated` with `error_code: null`)

**Solution**: Include a valid token in every request

### Forbidden Error

```json
{
  "detail": "This API key's scopes do not allow this request",
  "error_code": "api_key_scope_denied",
  "error_args": {}
}
```

**Causes** (`403`):
- API key has scoped access and lacks the required scope (`api_key_scope_denied`)
- The client address is refused by the instance's IP rules (`ip_not_allowed`, see below)
- The account is disabled (`detail`: `Account disabled`) or lacks the role the endpoint needs

**Solution**: Use a key with the appropriate scope or increase key privileges

### IP Rules

Administrators can restrict API access by client address under admin **Security → IP Rules**. A request from an address that matches a deny rule, or that matches no allow rule when allow rules exist, is refused before authentication:

```json
{
  "detail": "Access from this IP address is not allowed.",
  "error_code": "ip_not_allowed",
  "error_args": {}
}
```

`/api/version`, `/api/webhooks/` and CORS preflight requests are exempt. Behind a reverse proxy the instance must be told which proxy to trust (`FORWARDED_ALLOW_IPS`), otherwise every request appears to come from the proxy; see [Environment Variables](/configuration/environment-variables#platform).

### Expired Token

```json
{
  "detail": "Token has expired",
  "error_code": null,
  "error_args": {}
}
```

On the SSE endpoints, which read the token from the request body, the same condition returns `error_code` `token_expired`.

**Solution**: Use the refresh token to get a new access token:

```bash
curl -X POST https://your-domain.com/api/auth/refresh \
  -H "Content-Type: application/json" \
  -d '{"refresh_token": "your_refresh_token"}'
```

## Configuration des variables d'environnement

### Python

```python
import os
from dotenv import load_dotenv
import requests

# Load from .env file
load_dotenv()

api_key = os.getenv("FIM_API_KEY")
base_url = os.getenv("FIM_API_BASE_URL", "https://your-domain.com/api")

headers = {"Authorization": f"Bearer {api_key}"}

# Now use in requests
response = requests.get(f"{base_url}/agents", headers=headers)
```

### Node.js

```javascript
const api_key = process.env.FIM_API_KEY;
const base_url = process.env.FIM_API_BASE_URL || "https://your-domain.com/api";

const headers = {
  "Authorization": `Bearer ${api_key}`,
  "Content-Type": "application/json"
};

// Use in fetch
const response = await fetch(`${base_url}/agents`, {
  headers: headers
});
```

### Bash

```bash
#!/bin/bash

FIM_API_KEY="${FIM_API_KEY:-$(cat ~/.fim_api_key)}"
FIM_API_BASE_URL="${FIM_API_BASE_URL:-https://your-domain.com/api}"

curl -H "Authorization: Bearer $FIM_API_KEY" \
  "$FIM_API_BASE_URL/agents"
```

- Contact support if you believe a key has been compromised
