所有配置都通过 `.env` 完成。复制 `example.env` 并填入你的值：

```bash
cp example.env .env
```

## 配置级别

每个集成都有一个配置级别，表示其重要性：

| 级别 | 含义 | 未配置时的行为 |
|-------|---------|------------------------------|
| **必需** | 核心系统依赖 | 系统将出错 — 聊天和主要功能将无法工作 |
| **推荐** | 重要功能启用器 | 优雅降级 — 该功能明显不可用，但系统继续运行 |
| **可选** | 增强功能 | 透明降级 — 系统运行正常，该功能不存在 |

> **注意**：管理员配置的模型（管理员 → 模型页面）可以替代 LLM 环境变量。健康检查会考虑两个来源。

## 前端（仅本地开发）

前端有一个仅用于本地开发的独立环境文件：`frontend/.env.local`。

> **此文件在 Docker 中不使用。** 在 Docker 容器内，Next.js 在内部将 `/api/*` 代理到 Python 后端（端口 8000 是容器内部的），因此不需要前端环境文件。

对于本地开发，默认设置开箱即用 — 除非你的后端运行在非默认端口，否则**不需要**创建 `frontend/.env.local`。

如果需要覆盖，请手动创建 `frontend/.env.local`：

```bash
echo 'NEXT_PUBLIC_API_URL=http://localhost:9000' > frontend/.env.local
```

| 变量 | 默认值 | 描述 |
|---|---|---|
| `NEXT_PUBLIC_API_URL` | `http://localhost:8000` *（自动）* | **浏览器**用于直接 API 调用（OAuth 重定向、流式传输）的后端 URL。如果未设置，则从 `window.location` 自动检测 — 仅当后端在本地运行于非标准端口时才需覆盖。 |

> **构建时注意**：`NEXT_PUBLIC_*` 变量在 `pnpm build` 时被烘焙到 JS 包中。在运行时更改它们（例如通过根目录 `.env`）无效 — 这就是为什么它们仅存在于本地开发的 `frontend/.env.local` 中。

| `REASONING_LLM_BUDGET` | 否 | *（回退到 `LLM_REASONING_BUDGET_TOKENS`）* | 推理的令牌预算（主要用于 Anthropic）。覆盖推理层的自动计算预算 |
| `LLM_SUPPORTS_VISION` | 否 | `true` *（乐观）* | 控制是否尝试 ENV 模式文档 OCR（通过 MarkItDown + `markitdown-ocr`）。仅在**管理员 → 模型中未配置活跃模型组**时适用（纯 ENV 模式）。当默认 `true` 生效时，`convert_to_markdown` 和 RAG 摄取假设 `LLM_MODEL` 支持视觉并为图像 OCR 调用它——这对所有常见选择（`gpt-4o`、`claude-3-5-sonnet`、`gemini-1.5-pro/flash`）是正确的行为。当您的 ENV 配置的 `LLM_MODEL` **不**支持视觉时（例如 `deepseek-v3`、`qwen-chat`、`llama-3.1`、`gpt-3.5-turbo`、`o1-mini`），设置为 `false` 以跳过失败的视觉调用并直接进行纯文本提取。当管理员 → 模型面板中存在活跃模型组时，此标志被忽略，该组的 `supports_vision` 标志接管——管理员策划的选择始终是数据库模式中的真实来源。 |

> **解析顺序**：用户偏好 → 管理员模型（数据库）→ ENV 回退。如果在管理员 → 模型中配置了角色为"通用"的管理员模型，这些 ENV 变量仅作为回退。健康检查考虑两个来源。

### MarkItDown OCR 分辨率

`convert_to_markdown` 内置工具和 RAG 摄取管道都使用 Microsoft 的 [MarkItDown](https://github.com/microsoft/markitdown) + 官方 [`markitdown-ocr`](https://github.com/microsoft/markitdown/tree/main/packages/markitdown-ocr) 插件从文档中提取文本 — 包括在有支持视觉的 LLM 可用时对嵌入图像和扫描 PDF 页面进行 OCR。

**视觉 LLM 分辨率顺序**（首次匹配获胜）：

| # | 来源 | 优先级原因 |
|---|---|---|
| 1 | 智能体的**主要 LLM**（如果 `supports_vision=True`） | 一致性：相同的 API 密钥、相同的计费桶、与对话相同的速率限制池。 |
| 2 | 活跃的**模型组 → 快速模型**（如果 `supports_vision=True`） | 快速模型（`gpt-4o-mini`、`claude-haiku`、`gemini-1.5-flash`）是理想的 OCR 工具 — 便宜、低延迟、通常支持多模态。 |
| 3 | 活跃的**模型组 → 通用模型**（如果 `supports_vision=True`） | 当主要模型不在组中时的质量备选方案。 |
| 4 | **ENV 主要 LLM**（`LLM_MODEL`） | 纯 ENV 模式的乐观备选方案。仅在不存在活跃模型组时采用。由 `LLM_SUPPORTS_VISION` 控制。 |

**推理模型永远不会被优先选择用于 OCR。** 推理层级（`o1`、`o3-mini`、`DeepSeek-R1`）历来缺乏视觉支持，本身也不是 OCR 的合适工具 — OCR 是一项感知任务，而非推理任务。如果工作区仅有一个支持视觉的推理模型（`supports_vision=True`），它仍会通过主要 LLM 路径被选中，但解析器不会主动将其排名高于快速/通用模型。

**零回归备选方案**：当在任何级别都找不到支持视觉的模型时，OCR 会被静默禁用，MarkItDown 以纯文本模式运行。Word/PowerPoint/Excel 嵌入图像 OCR 变为不可用（与此功能发布前相同），但所有其他文本提取（标题、表格、段落文本）继续正常工作。**不存在添加此功能使提取效果比之前行为更差的情况。**

**非 OpenAI 提供商（Anthropic、Google Gemini 等）** 得到透明支持：解析的 LLM 被包装在 `LiteLLMOpenAIShim` 中，该 shim 将 `chat.completions.create(...)` 调用路由通过 `litellm.completion()`，后者处理提供商特定的消息格式转换（例如 Anthropic 的 `source.type="base64"` 图像块）。一个 shim 覆盖 LiteLLM 支持的每个提供商 — 添加新提供商在 FIM One 中零代码更改成本。

### 扩展思维（推理）

当设置 `LLM_REASONING_EFFORT` 时，FIM One 启用模型的扩展思维能力，使内部思维链在 UI 的"思维"步骤中显示。FIM One 使用 [LiteLLM](https://github.com/BerriAI/litellm) 自动将推理努力参数转换为每个提供商的原生格式。

#### 支持的提供商

哪些提供商接受思考、如何启用每个提供商、它采用哪些`effort`值，以及推理文本最终出现在哪里，这些信息都记录在[提供商能力矩阵的表C](/architecture/llm-provider-guide#provider-capability-matrix)中，并带有代码锚点。该表是权威列表；本页面仅记录变量。

FIM One从`LLM_BASE_URL`解析提供商（加上配置时的显式提供商字段），并将请求映射到正确的API格式。未知的URL被视为OpenAI兼容。

#### 重要注意事项

<Warning>
**第三方代理 / 自定义端点不保证兼容。**
如果您的 `LLM_BASE_URL` 指向第三方 API 代理（例如 OpenRouter、one-api、自定义网关），LiteLLM 将尝试根据 URL 正确路由。但是，如果您的代理需要非标准格式，推理可能无法按预期工作。请查阅代理的文档以了解其预期的参数格式。
</Warning>

#### 推理时的温度约束

某些提供商在启用推理时会限制`temperature`。**这些限制都会自动强制执行；请根据您的工作负载需求设置`LLM_TEMPERATURE`。**

- **Anthropic**：启用扩展思考时需要`temperature=1`。请求构建器会在Anthropic路由上固定该值，因此您配置的温度会被这些调用覆盖，而不是被拒绝。
- **Anthropic、严格模型**（Opus 4.7和4.8、Fable 5、Mythos 5）：无论是否启用思考，都会直接拒绝`temperature`、`top_p`和`top_k`。FIM One会从这些模型的请求中移除`temperature`。
- **OpenAI GPT-5.x**：仅支持`temperature=1`。LiteLLM的`drop_params`过滤会移除不支持的值。

手动设置`LLM_TEMPERATURE=1`来满足Anthropic的要求是不必要的，这样做会让您无法在每个非思考调用上运行更低的温度。

#### `LLM_REASONING_BUDGET_TOKENS` 的工作原理

此变量**仅在旧版 Anthropic 思考路径上有意义**（Claude 4.5 及更早版本，路由为 `anthropic/`）。在该路径上，它会覆盖自动计算的预算，并作为 `budget_tokens` 在 `thinking` 参数内发送。自适应思考模型（Opus 4.6 及更新版本、Sonnet 4.6、Fable 5、Mythos 5）采用努力级别而非预算，完全忽略此变量。未设置时，预算从 `LLM_MAX_OUTPUT_TOKENS` × 努力比率推导：

| `LLM_REASONING_EFFORT` | 预算比率 | 示例（max_tokens = 64000） |
|---|---|---|
| `low` | 20% | 12,800 tokens |
| `medium` | 50% | 32,000 tokens |
| `high` | 80% | 51,200 tokens |

最小预算为 1,024 tokens（Anthropic 的硬性最低值）。

对于 OpenAI 和 Gemini，提供商根据 `reasoning_effort` 级别在内部处理令牌分配——`LLM_REASONING_BUDGET_TOKENS` 无效。

## 智能体执行

### ReAct 智能体

| 变量 | 必需 | 默认值 | 描述 |
|---|---|---|---|
| `REACT_MAX_ITERATIONS` | 否 | `20` | 每个 ReAct 请求的最大工具调用迭代次数。值越高越彻底，但速度越慢且成本越高 |
| `REACT_MAX_TURN_TOKENS` | 否 | `0` | 紧急断路器：单个 ReAct 轮次的最大累积令牌数（所有迭代的提示词 + 完成）。默认 `0` = 无限制。**这不是用于日常令牌控制的**——请使用按用户的 `token_quota`。这是针对极端场景（如智能体陷入无限工具调用循环）的最后防线。触发此限制会中止任务执行，浪费已消耗的所有令牌并返回不完整结果。除非有特定的失控智能体问题需要处理，否则保持为 `0` |
| `REACT_TOOL_SELECTION_THRESHOLD` | 否 | `12` | 当注册工具总数超过此阈值时，轻量级 LLM 调用会在每个请求前选择最相关的子集 |
| `REACT_TOOL_SELECTION_MAX` | 否 | `6` | 智能选择后保留的最大工具数（仅当工具数超过 `REACT_TOOL_SELECTION_THRESHOLD` 时有效） |
| `REACT_SELF_REFLECTION_INTERVAL` | 否 | `6` | 每 N 次工具调用后注入一次自反思提示词，帮助智能体纠正方向并避免循环 |
| `REACT_TOOL_OBS_TRUNCATION` | 否 | `8000` | 合成最终答案时每个工具观察的最大字符数。较高的值保留更多结构化数据（JSON、表格），但消耗更多令牌 |
| `REACT_TOOL_RESULT_BUDGET` | 否 | `40000` | 单个会话中所有工具结果的聚合令牌预算。当工具结果令牌总数超过此上限时，新结果会被截断并附加通知。防止大型 API 响应（例如 5 个连接器调用各返回 8K）导致的上下文膨胀。设为 `0` 禁用此上限 |
| `REACT_COMPLETION_CHECK_SKIP_CHARS` | 否 | `800` | 当智能体的最终答案超过此字符数时，跳过答案后完成度检查 LLM 调用。长详细答案不需要"我是否遗漏了什么？"验证往返。设置较低值可更激进地跳过；设置为非常大的值可始终运行检查 |
| `REACT_CYCLE_DETECTION_THRESHOLD` | 否 | `2` | 当同一工具连续以相同参数调用此次数时，会注入确定性警告，告诉智能体尝试不同方法。与依赖 LLM 发现循环的自反思不同，这是基于哈希的检查，无法被绕过。也适用于 DAG 步骤 |
| `REACT_COMPLETION_CHECK_MIN_TOOLS` | 否 | `3` | 完成度检查清单启动前的最小工具调用次数。简单任务（1-2 次工具调用）跳过验证以避免不必要的延迟。设为 `1` 可始终启用验证。也适用于 DAG 步骤 |
| `REACT_TURN_PROFILE_ENABLED` | 否 | `true` | 发出按轮次阶段级别的计时日志（`memory_load`、`compact`、`tool_schema_build`、`llm_first_token`、`llm_total`、`tool_exec`）。每轮一行结构化日志。设为 `false` 禁用分析（零开销） |
| `REACT_PLAN_TOOL_ENABLED` | 否 | `true` | 注册 `update_plan` 待办工具，使智能体在多步任务期间记录和维护计划检查清单。对于 DAG 步骤智能体和无工具的智能体自动跳过 |
| `REACT_PLAN_REMINDER_INTERVAL` | 否 | `3` | 在注入陈旧计划提醒前，未调用 `update_plan` 的工具轮次数（嵌入完整检查清单），使计划在上下文压缩中保留 |
| `REACT_PLAN_REPEAT_THRESHOLD` | 否 | `4` | 连续轮次调用同一工具（使用不同参数）的次数，之后提醒告诉智能体改变方法而不是重复无效调用。完全重复的调用由循环检测单独处理 |
| `REACT_PLAN_NUDGE_AFTER` | 否 | `5` | 未记录计划的工具轮次数，之后一次性推动建议记录计划。仅在计划工具启用时适用 |
| `REACT_FINISH_SIGNAL` | 否 | `true` | 聊天路径上的 FINAL 优先应答：智能体在 `finish` 信号上结束工具循环，然后将答案作为真正令牌流式传输的轮次写入。设为 `false` 恢复内联循环答案与缓冲重放 |
| `REACT_MAX_CONTINUATIONS` | 否 | `3` | 当模型答案被提供商的输出令牌限制截断时的最大续接轮次（`finish_reason=length`）。截断的段落被拼接成一个无缝答案，既在智能体循环中也在流式合成中 |
| `REACT_BACKGROUND_TOOLS_ENABLED` | 否 | `true` | 在慢速工具（沙箱 python/shell/node 执行）上提供 `run_in_background` 选项。智能体立即获得任务 id 并继续工作；工具完成时结果作为 `<task_notification>` 消息到达 |
| `REACT_BG_WAIT_TIMEOUT` | 否 | `300` | 智能体想要最终确定答案时等待仍在运行的后台工具的最大秒数。窗口内未完成的任务被取消并显示明确的超时通知 |
| `DAG_CHECKPOINT_EVIDENCE_CHARS` | 否 | `4000` | DAG 崩溃恢复检查点文件（`data/dag_checkpoints/`）中每步的证据上限。步骤摘要完整存储 |
| `DAG_CHECKPOINT_MAX_AGE_HOURS` | 否 | `24` | 超过此时间的 DAG 检查点在加载时被忽略，因此陈旧的崩溃遗留物永远不会恢复到新运行中 |
| `LLM_RATE_LIMIT_PER_USER` | 否 | `true` | 使用按用户键控的速率限制桶而不是单个进程全局桶。防止一个嘈杂用户在同一工作进程上饿死所有其他用户。底层速率硬编码为每个桶每分钟 60 个请求和 100K 个令牌——此设置仅控制桶是共享（全局）还是分区（按用户）。设为 `false` 恢复到旧版全局桶（不推荐） |

### DAG 规划器

| 变量 | 必需 | 默认值 | 描述 |

| `MAX_CONCURRENCY` | 否 | `5` | DAG 执行器中的最大并行步骤数 |
| `DAG_STEP_MAX_ITERATIONS` | 否 | `15` | 每个 DAG 步骤内的最大工具调用迭代次数 |
| `DAG_STEP_TIMEOUT` | 否 | `600` | 步骤执行超时时间（秒）。超过此时间的步骤标记为失败，其依赖步骤级联跳过 |
| `DAG_MAX_REPLAN_ROUNDS` | 否 | `3` | 目标未达成时的最大自主重新规划尝试次数。用户中断（注入）次数不限，不计入此预算 |

| `DAG_VERIFY_TRUNCATION` | 否 | `2000` | 发送给步骤验证器 LLM 进行质量判断的步骤输出最大字符数 |

| `DAG_STEP_EVIDENCE_CHARS` | 否 | `16000` | 每个步骤保留的原始工具输出（网页获取、搜索结果、文件读取）最大字符数，作为权威"源证据"。这些数据与步骤的摘要一起提供给分析器和最终合成，以便答案的事实声明（总数、枚举、严重程度）可以针对源进行验证，而不是依赖可能已无声地丢弃或错误标记项目的摘要。设置为 `0` 禁用证据捕获 |
| `DAG_REPLAN_RECENT_TRUNCATION` | 否 | `500` | 构建重新规划上下文时来自最近一轮的每个步骤结果的最大字符数 |

| `DAG_CITATION_VERIFY_TRUNCATION` | 否 | `6000` | 发送给引用验证提示的步骤结果最大字符数 |

## RAG 与知识库（推荐）

### 嵌入

嵌入将文本转换为向量以进行知识库搜索。FIM One 使用标准的 **OpenAI 兼容 `/v1/embeddings` 端点**，因此它适用于任何公开此接口的提供商 — 不仅仅是 Jina。

| 变量 | 必需 | 默认值 | 描述 |
|---|---|---|---|
| `EMBEDDING_API_KEY` | 否 | *(回退到 `JINA_API_KEY`)* | 嵌入提供商的 API 密钥 |
| `EMBEDDING_BASE_URL` | 否 | `https://api.jina.ai/v1` | 嵌入提供商的基础 URL |
| `EMBEDDING_MODEL` | 否 | `jina-embeddings-v3` | 模型标识符 |
| `EMBEDDING_DIMENSION` | 否 | `1024` | 向量维度 |

**提供商示例** — 只需设置这三个变量即可切换：

| 提供商 | `EMBEDDING_BASE_URL` | `EMBEDDING_MODEL` | `EMBEDDING_DIMENSION` |
|---|---|---|---|
| **Jina** *(默认)* | `https://api.jina.ai/v1` | `jina-embeddings-v3` | `1024` |
| **OpenAI** | `https://api.openai.com/v1` | `text-embedding-3-small` | `1536` |
| **Voyage** | `https://api.voyageai.com/v1` | `voyage-3` | `1024` |
| **Ollama** *(本地)* | `http://localhost:11434/v1` | `nomic-embed-text` | `768` |

<Warning>
**更改嵌入模型或维度会使所有现有知识库向量失效。** 旧向量是在不同的嵌入空间中计算的 — 检索准确性将无声地降低。切换后，您必须**重建所有知识库索引**。
</Warning>

| `DATABASE_URL` | 否 | `sqlite+aiosqlite:///./data/fim_one.db` | 数据库连接字符串。**SQLite**（零配置）：`sqlite+aiosqlite:///./data/fim_one.db`。**PostgreSQL**（生产环境）：`postgresql+asyncpg://user:pass@localhost:5432/fim_one`。Docker Compose自动配置PostgreSQL。 |
| `JWT_SECRET_KEY` | 否 | `CHANGE_ME` | JWT令牌签名的密钥。占位符值`CHANGE_ME`（或任何旧版默认值）会在首次启动时触发自动生成安全的256位随机密钥，并写回`.env`。在生产环境中显式设置以保持令牌在重启和副本间的有效性。 |
| `FIM_BCRYPT_COST` | 否 | `12` | bcrypt工作因子用于密码哈希，范围限制在4-31。默认值12在现代CPU上每次哈希耗时约200ms；在弱硬件上降低该值，在安全加固的部署中提高该值。 |
| `CORS_ORIGINS` | 否 | — | 逗号分隔的额外允许CORS源列表，超出默认localhost条目。当前端运行在非localhost域名上时需要（例如`https://app.example.com`）。 |
| `UPLOADS_DIR` | 否 | `./uploads` | 上传文件的目录 |
| `EXPORT_FONT_DIR` | 否 | *（自动检测）* | 存放`NotoSansSC-Regular.ttf` / `NotoSansSC-Bold.ttf`的目录，用于PDF导出。使用`python scripts/fetch_export_fonts.py`获取；Docker镜像已内置。没有可嵌入的TrueType CJK字体时，PDF导出会回退到非嵌入式CID字体，导致间距降级且无粗体。 |
| `MAX_UPLOAD_SIZE_MB` | 否 | `50` | 最大文件上传大小（单位：MB，后端强制） |
| `NEXT_PUBLIC_MAX_UPLOAD_SIZE_MB` | 否 | `50` | 前端UI显示的最大文件上传大小。**构建时变量**——必须与`MAX_UPLOAD_SIZE_MB`匹配。 |
| `MCP_SERVERS` | 否 | — | MCP服务器配置的JSON数组（需要`uv sync --extra mcp`） |
| `ALLOW_STDIO_MCP` | 否 | `false` | 允许stdio MCP服务器。仅在受信任的本地部署中设置为`true` |
| `ALLOWED_STDIO_COMMANDS` | 否 | `npx,uvx,node,python,python3,deno,bun` | stdio MCP服务器允许的基础命令的逗号分隔列表。仅在`ALLOW_STDIO_MCP=true`时生效 |
| `LOG_LEVEL` | 否 | `INFO` | 日志级别：`DEBUG` / `INFO` / `WARNING` / `ERROR` / `CRITICAL` |
| `REDIS_URL` | 否 | — | Redis连接URL用于跨工作进程中断中继。**当`WORKERS>1`时必需**——没有它，中流中断/注入请求可能会命中不同的工作进程而无声失败。由Docker Compose自动配置。 |
| `WORKERS` | 否 | `1` | Uvicorn工作进程数。`1`是安全的，不需要外部服务。对于生产多工作进程，使用PostgreSQL（SQLite是单写入器）。SQLite在轻负载下适合本地开发。身份验证、OAuth和文件操作完全支持多工作进程（基于JWT）。Docker Compose自动配置PostgreSQL和Redis。 |

<Warning>
**多工作进程检查清单**（`WORKERS>1`）：
- **停止（中止流式传输）**——始终有效，无需额外配置（信号在同一TCP连接上传输）。
- **注入（中流后续）**——**需要`REDIS_URL`**。没有Redis，注入请求可能落在不同的工作进程上，该进程不知道正在运行的执行，导致无声失败。
- **生产环境**：使用PostgreSQL（`DATABASE_URL`）。SQLite的单写入器锁在并发写入下可能导致争用。
- **本地开发**：SQLite+多工作进程在轻使用下可以接受；如果使用注入功能，只需添加`REDIS_URL`。
</Warning>

## 工作流运行保留

自动清理旧工作流运行的后台任务。按工作流的覆盖设置（在工作流设置UI中配置）优先于这些全局默认值。

| 变量 | 必需 | 默认值 | 描述 |
|---|---|---|---|
| `WORKFLOW_RUN_MAX_AGE_DAYS` | 否 | `30` | 删除早于此天数的工作流运行 |
| `WORKFLOW_RUN_MAX_PER_WORKFLOW` | 否 | `100` | 每个工作流最多保留此数量的运行（最旧的优先删除） |
| `WORKFLOW_RUN_CLEANUP_INTERVAL_HOURS` | 否 | `24` | 后台清理任务运行的频率，单位为小时 |

### 通道确认请求过期

后台清理程序，将陈旧的待审批请求（由通道钩子如 `FeishuGateHook` 或审批演练场产生）标记为已过期。确保稍后点击被遗忘的卡片不会翻转已被拆除的智能体状态。

| 变量 | 必需 | 默认值 | 描述 |
|---|---|---|---|
| `CHANNEL_CONFIRMATION_TTL_MINUTES` | 否 | `1440` | 超过此时间的待确认请求将自动过期（默认值：24小时） |
| `CHANNEL_CONFIRMATION_SWEEP_INTERVAL_SECONDS` | 否 | `600` | 过期清理程序运行的频率（默认值：每10分钟） |

## Cloudflare Tunnel（可选）

通过 Cloudflare 的网络路由所有流量，而不是直接暴露端口。无需 Nginx、SSL 证书和开放防火墙规则。有关设置说明，请参阅[生产部署](/quickstart#cloudflare-tunnel)部分。

<Warning>
**中国大陆用户**：Cloudflare Free/Pro/Business 计划在中国大陆没有 PoP。流量被路由到海外边缘节点，导致频繁出现 502 错误。除非您拥有带有中国网络的 Cloudflare Enterprise，否则如果您的主要用户在中国大陆，请勿使用此功能。
</Warning>

| 变量 | 必需 | 默认值 | 描述 |
|---|---|---|---|
| `CLOUDFLARE_TUNNEL_TOKEN` | **是**（如果使用 Tunnel） | — | 来自 Cloudflare Zero Trust → Networks → Tunnels → 您的 tunnel → Configure 的令牌。以 `eyJ...` 开头。由 `docker-compose.tunnel.yml` 中的 `cloudflared` sidecar 所需。 |

## Stripe 计费（可选）

Stripe 为 Pro 订阅提供支持。将所有三个变量留空可禁用计费——FIM One 的其余部分保持不变。**必须**同时设置 `STRIPE_SECRET_KEY` **和** `STRIPE_WEBHOOK_SECRET`；部分配置会在首次使用时引发错误。

| 变量 | 必需 | 默认值 | 描述 |
|---|---|---|---|
| `STRIPE_SECRET_KEY` | 否 | — | Stripe API 密钥。必须以 `sk_test_` / `sk_live_`（完全访问权限）或 `rk_test_` / `rk_live_`（受限密钥）开头。从 Stripe Dashboard → Developers → API keys 获取。切勿将 `sk_live_*` 密钥提交到源代码。 |
| `STRIPE_WEBHOOK_SECRET` | 否 | — | Stripe webhook 签名密钥（`whsec_*`）。在 Stripe Dashboard → Developers → Webhooks → Add endpoint 中注册 webhook 端点时创建。验证入站 webhook 负载所需。 |
| `STRIPE_BILLING_RETURN_URL` | 否 | `http://localhost:3000/settings?tab=billing` | Stripe 在 Checkout / Customer Portal 会话后重定向用户的 URL。将其设置为生产环境计费设置页面（例如 `https://your-domain.com/settings?tab=billing`）。 |
