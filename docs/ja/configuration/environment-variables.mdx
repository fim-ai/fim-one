すべての設定は `.env` を使用して行われます。`example.env` をコピーして値を入力してください：

```bash
cp example.env .env
```

## 設定レベル

各統合には、その重要度を示す設定レベルがあります：

| レベル | 意味 | 設定されていない場合の動作 |
|-------|---------|------------------------------|
| **Required** | コアシステム依存 | システムがエラーになります — チャットと主要機能は動作しません |
| **Recommended** | 重要な機能の有効化 | グレースフルデグラデーション — 機能は目に見える形で利用不可になりますが、システムは実行されます |
| **Optional** | 拡張機能 | 透過的デグラデーション — システムは正常に動作し、機能は単に存在しません |

> **注**: 管理者が設定したモデル（Admin → Models ページ）は、LLM 環境変数の代わりになります。ヘルスチェックは両方のソースを考慮します。

## フロントエンド（ローカル開発のみ）

フロントエンドには**ローカル開発のみ**の別の環境ファイルがあります：`frontend/.env.local`。

> **このファイルは Docker では使用されません。** Docker コンテナ内では、Next.js が `/api/*` を Python バックエンドに内部的にプロキシします（ポート 8000 はコンテナ内部）ため、フロントエンド環境ファイルは不要です。

ローカル開発では、デフォルト設定がそのまま機能します — バックエンドがデフォルトポートで実行されている場合、`frontend/.env.local` を作成する**必要はありません**。

オーバーライドが必要な場合は、`frontend/.env.local` を手動で作成してください：

```bash
echo 'NEXT_PUBLIC_API_URL=http://localhost:9000' > frontend/.env.local
```

| 変数 | デフォルト | 説明 |
|---|---|---|
| `NEXT_PUBLIC_API_URL` | `http://localhost:8000` *(自動)* | **ブラウザ**が直接 API 呼び出し（OAuth リダイレクト、ストリーミング）に使用するバックエンド URL。未設定の場合は `window.location` から自動検出されます — ローカルでバックエンドが非標準ポートで実行されている場合のみオーバーライドしてください。 |

> **ビルド時の注意**：`NEXT_PUBLIC_*` 変数は `pnpm build` 時に JS バンドルに埋め込まれます。実行時に変更する場合（例：ルート `.env` 経由）は効果がありません — これが、ローカル開発のみで `frontend/.env.local` に配置される理由です。

### ENV フォールバックを管理パネルと同期させる

Admin → Models でモデルグループを有効にすると、ランタイムはそのグループからモデルを取得し、上記の `LLM_*` / `FAST_LLM_*` / `REASONING_LLM_*` の値はフォールバックとしてのみ使用されます。データベースを開かない補助経路では、これらの値が直接読み取られます。対象となるのは、`scripts/translate.py`（国際化の pre-commit フック）、`evals/`、Jina/OpenAI のリランカー、画像生成です。これらが古いプロバイダーを参照し続けるのを防ぐには、アクティブなグループを env ファイルにコピーします。

```bash
uv run scripts/env_from_active_group.py --dry-run     # show what would change, keys masked
uv run scripts/env_from_active_group.py               # rewrite .env (backup in .env.bak)
uv run scripts/env_from_active_group.py --image-gen   # also point IMAGE_GEN_* at the general provider
```

スクリプトは ORM を介してプロバイダーキーを読み取り、そのままファイルに書き込みます。内容が出力されることはありません。完了後、アプリを再起動してください。

### MarkItDown OCR Resolution

The `convert_to_markdown` built-in tool and the RAG ingestion pipeline both use Microsoft's [MarkItDown](https://github.com/microsoft/markitdown) + the official [`markitdown-ocr`](https://github.com/microsoft/markitdown/tree/main/packages/markitdown-ocr) plugin to extract text from documents — including OCR on embedded images and scanned PDF pages when a vision-capable LLM is available.

The tool reads two kinds of source: a file the calling user uploaded, named by its `file_id`, and an `http://` or `https://` URL. URLs are downloaded with the same restrictions as `web_fetch` and `http_request` (no private, loopback, link-local or metadata addresses, redirects included). Local paths, `file://`, `data:` and other schemes are refused.

**Vision LLM resolution order** (first match wins):

| # | Source | Priority rationale |
|---|---|---|
| 1 | Agent's **primary LLM** if `supports_vision=True` | Consistency: same API key, same billing bucket, same rate-limit pool as the conversation. |
| 2 | Active **ModelGroup → Fast Model** if `supports_vision=True` | Fast models (`gpt-4o-mini`, `claude-haiku`, `gemini-1.5-flash`) are the ideal OCR workhorse — cheap, low-latency, usually multimodal. |
| 3 | Active **ModelGroup → General Model** if `supports_vision=True` | Quality fallback when the primary is not in the group. |
| 4 | **ENV primary LLM** (`LLM_MODEL`) | Optimistic fallback for pure ENV mode. Only taken when no active ModelGroup exists. Gated by `LLM_SUPPORTS_VISION`. |

**Reasoning models are never preferred for OCR.** Reasoning tiers (`o1`, `o3-mini`, `DeepSeek-R1`) historically lack vision support and are the wrong tool for OCR anyway — OCR is a perception task, not deliberation. If a workspace has only a reasoning model with `supports_vision=True` it will still be picked up via the primary-LLM path, but the resolver does not actively rank it above fast/general.

**Zero-regression fallback**: when no vision-capable model is found at any level, OCR is silently disabled and MarkItDown runs in text-only mode. Word/PowerPoint/Excel embedded-image OCR becomes unavailable (same as before this feature shipped), but all other text extraction (headings, tables, paragraph text) continues to work unchanged. **There is never a case where adding this feature made extraction worse than the previous behavior.**

**Non-OpenAI providers (Anthropic, Google Gemini, etc.)** are supported transparently: the resolved LLM is wrapped in a `LiteLLMOpenAIShim` that routes `chat.completions.create(...)` calls through `litellm.completion()`, which handles the provider-specific message format translation (e.g. Anthropic's `source.type="base64"` image block). One shim covers every provider LiteLLM supports — adding a new provider costs zero code changes in FIM One.

### 拡張思考（推論）

`LLM_REASONING_EFFORT` が設定されると、FIM One はモデルの拡張思考機能を有効にし、内部の思考の連鎖を UI の「thinking」ステップで表示します。FIM One は [LiteLLM](https://github.com/BerriAI/litellm) を使用して、推論努力パラメータを各プロバイダーのネイティブ形式に自動的に変換します。

#### サポートされているプロバイダー

どのプロバイダーが思考を受け入れるか、それぞれがどのように有効にされるか、どの`effort`値を取るか、推論テキストがどこに終わるかは、[プロバイダー機能マトリックスの表C](/architecture/llm-provider-guide#provider-capability-matrix)にコードアンカー付きで一度記録されます。その表が信頼できるリストです。このページは変数のみを文書化しています。

FIM Oneは`LLM_BASE_URL`からプロバイダーを解決し（1つが設定されている場合は明示的なプロバイダーフィールドを追加）、リクエストを正しいAPI形式にマップします。未知のURLはOpenAI互換として扱われます。

#### 重要な注意事項

<Warning>
**サードパーティプロキシ / カスタムエンドポイントは保証されません。**
`LLM_BASE_URL` がサードパーティ API プロキシ (例: OpenRouter、one-api、カスタムゲートウェイ) を指している場合、LiteLLM は URL に基づいて正しくルーティングしようとします。ただし、プロキシが非標準形式を期待している場合、推論が期待どおりに機能しない可能性があります。プロキシのドキュメントで、期待されるパラメータ形式を確認してください。
</Warning>

#### 推理時の温度制約

推理がアクティブな場合、一部のプロバイダーは`temperature`を制限します。**これらはすべて自動的に適用されます。`LLM_TEMPERATURE`は、ワークロードに適した値のままにしてください。**

- **Anthropic**: 拡張思考が有効な場合、`temperature=1`が必須です。リクエストビルダーはAnthropicルートで値をピン留めするため、設定された温度は拒否されるのではなく、これらの呼び出しでオーバーライドされます。
- **Anthropic、厳密なモデル**（Opus 4.7および4.8、Fable 5、Mythos 5）: 思考の有無に関わらず、`temperature`、`top_p`、`top_k`を完全に拒否します。FIM Oneはこれらのモデルのリクエストから`temperature`を削除します。
- **OpenAI GPT-5.x**: `temperature=1`のみをサポートします。LiteLLMの`drop_params`フィルタリングはサポートされていない値を削除します。

Anthropicを満たすために手動で`LLM_TEMPERATURE=1`を設定することは不要であり、思考以外のすべての呼び出しでより低い温度を実行する能力を失うコストがかかります。

#### `LLM_REASONING_BUDGET_TOKENS` の動作

この変数は**レガシーAnthropicシンキングパス上でのみ意味があります**（Claude 4.5以前、`anthropic/`としてルーティング）。ここでは自動計算されたバジェットをオーバーライドし、`thinking`パラメータ内の`budget_tokens`として送信されます。アダプティブシンキングモデル（Opus 4.6以降、Sonnet 4.6、Fable 5、Mythos 5）はバジェットの代わりにエフォートレベルを使用し、この変数は完全に無視されます。設定されていない場合、バジェットは`LLM_MAX_OUTPUT_TOKENS` x エフォート比率から導出されます：

| `LLM_REASONING_EFFORT` | バジェット比率 | 例（max_tokens = 64000） |
|---|---|---|
| `low` | 20% | 12,800 tokens |
| `medium` | 50% | 32,000 tokens |
| `high` | 80% | 51,200 tokens |

最小バジェットは1,024トークン（Anthropicのハード最小値）です。

OpenAIおよびGeminiの場合、プロバイダーは`reasoning_effort`レベルに基づいて内部的にトークン割り当てを処理します——`LLM_REASONING_BUDGET_TOKENS`は効果がありません。

| `DAG_REPLAN_STOP_CONFIDENCE` | No | `0.8` | Applies only when the agent judges the goal **unreachable** (impossible request, missing capability, dead resource): stop retrying at or above this certainty. ### ドメイン分類

ReAct と DAG 実行の**前に**実行される独立した LLM ベースのドメイン検出レイヤーを制御します。クエリが専門ドメインとして分類されると、システムはドメイン対応機能をアクティブ化します：モデルのエスカレーション、ドメイン固有の SOP 指示、および引用検証（DAG のみ）。

| 変数 | 必須 | デフォルト | 説明 |
|---|---|---|---|
| `ESCALATION_DOMAINS` | いいえ | `legal,medical,financial,tax,compliance,patent` | 専門ドメインのカンマ区切りリスト。高速 LLM が各クエリをこのリストに対して分類します。マッチした場合、システムは以下を実行します：(1) より高い精度を得るために推論モデルにアップグレード、(2) ドメイン固有の SOP 指示を注入（例：書き込み前に検索で引用を検証）、(3) DAG ステップの引用検証を有効化。必要に応じてカスタムドメインを追加します（例：`legal,education,construction`） |

埋め込みはテキストをベクトルに変換し、ナレッジベース検索に使用します。FIM One は標準的な **OpenAI互換の `/v1/embeddings` エンドポイント**を使用するため、Jina だけでなく、このインターフェースを公開しているあらゆるプロバイダーで動作します。

| プロバイダー | `EMBEDDING_BASE_URL` | `EMBEDDING_MODEL` | `EMBEDDING_DIMENSION` |

### Verification code limits

Emailed codes (sign-in, registration, password reset) allow five tries each. These settings bound how many codes are issued and tried; `0` switches a rule off. Counting is done in the database, so the limits hold across workers and under simultaneous requests. Windows are aligned to the clock.

| Variable | Required | Default | Description |
|---|---|---|---|
| `AUTH_CODE_SENDS_BEFORE_COOLDOWN` | No | `3` | Codes issued per address and purpose each day (UTC) before a wait applies |
| `AUTH_CODE_SEND_COOLDOWN_MAX_MINUTES` | No | `60` | Longest wait between codes for one address and purpose. The wait starts at one minute after the codes above and doubles with each code up to this value, which also bounds the codes per address a day (about 30 with the defaults). The wait is shared by everyone requesting codes for the address. `0` switches the wait off |
| `AUTH_CODE_SENDS_PER_IP_HOUR` | No | `30` | Anonymous requests for a code per client address per hour |
| `AUTH_CODE_CHECKS_PER_IP_HOUR` | No | `60` | Anonymous attempts to use a code per client address per hour |
| `AUTH_CODE_TRIES_PER_CLIENT` | No | `3` | Anonymous tries of one code from one client address, of the code's five |

Addresses are compared without case and without a trailing dot of the domain (`name@example.com.` counts as `name@example.com`). A request over a limit is answered with HTTP 429 (`verification_rate_limited`) before the address is looked up, so the answer is the same whether or not the address has an account. A signed-in request for a reset code is counted under the account, separately from anonymous requests for the same address. The client address is the one the application server sees: behind a reverse proxy, run the server so that it trusts the proxy's forwarded address, otherwise all clients share one count.

Requests for a sign-in or reset code are answered the same way whether or not the address has an account; a code is mailed only to an active account's address.

### Database connectors on internal networks

A database connector dials the host and port its creator entered, from the application server. So that a connector cannot be pointed at the application's own database, at other services on the server's network or at a cloud metadata address, the host is resolved by the application and every address it resolves to must be public. The check runs when a connector is saved, when a connection is tested and each time a connection pool is opened, and the driver then connects to the address that was checked.

Private deployments usually do need internal databases. Allow them explicitly:

```bash
# one database
DB_CONNECTOR_ALLOWED_HOSTS=10.20.30.40:5432
# a database subnet and one named host
DB_CONNECTOR_ALLOWED_HOSTS=10.20.0.0/16,erp-db.corp.internal:3306
```

- An address or network entry allows a target when all the internal addresses it resolves to fall inside the entry.
- A host-name entry allows that name as it is typed in the connector, whatever it resolves to. `*.suffix` matches any name ending in `.suffix`.
- A `:port` suffix limits the entry to that port.
- The rule applies to every user, administrators included: the allow-list is the one place where internal reach is granted.
- The hosts of `DATABASE_URL` and of `REDIS_URL` (also a `?host=` parameter and each host of a multi-host URL) are refused on every port, even when an entry covers them. They are compared by the addresses they resolve to; if one of them cannot be resolved, every database connector is refused and the server log names the host.
- One entry that cannot be parsed refuses every database connector, public targets included, until it is corrected. Users are told that the setting is invalid; the entry itself is written to the server log.
- List the networks and hosts your databases are on. An entry such as `0.0.0.0/0` or `::/0` allows every internal address, cloud metadata addresses included, and turns the check off.

After an upgrade, existing connectors that point at internal hosts answer "This database host is on an internal network" until the host is added here and the application restarted. The host field itself takes a bare host name or IP address: no `user:password@`, port, path or list of hosts.

A run still `running` whose stamp is stale was being executed by a process that no longer exists: it is closed as failed, its open approval requests are closed and its working directory is removed. ## Audit Record Retention

A daily background sweep removes audit records older than their retention period, in small batches. Every sweep leaves one `audit.retention_sweep` entry in the audit log with the number of rows removed from each table. With several replicas, one of them sweeps: on PostgreSQL they agree through a session-level advisory lock, so `DATABASE_URL` must reach the database directly or through a pooler in session mode. Behind a pooler in transaction mode (PgBouncer's `pool_mode = transaction`, a Supabase or Neon pooled port) the lock is taken and released on different server sessions; the sweeper then logs a warning and closes the connection. The usage ledger is never swept. The first sweep runs within ten minutes of the first start on a version that has it: set a variable to `0` beforehand to keep older records.

| Variable | Required | Default | Description |
|---|---|---|---|
| `AUDIT_RETENTION_DAYS` | No | `365` | How long the audit log, the sign-in history and organizations' review trails are kept. A value from 1 to 179 is raised to `180`. At the same age the arguments stored with a decided approval request are cleared; the request and its decision stay. `0` keeps everything for ever |
| `CALL_LOG_RETENTION_DAYS` | No | `180` | How long the records of calls to connectors, databases and MCP servers are kept. `0` keeps them for ever |

## Cloudflare Tunnel（オプション）

Cloudflareのネットワークを通じてすべてのトラフィックをルーティングし、ポートを直接公開しません。Nginx、SSLサーティフィケート、ファイアウォールルールを開く必要がなくなります。セットアップ手順については、[本番環境デプロイメント](/quickstart#cloudflare-tunnel)セクションを参照してください。

<Warning>
**中国本土ユーザー**: Cloudflare Free/Pro/Businessプランは中国本土にPoP（Point of Presence）がありません。トラフィックは海外のエッジにルーティングされ、502エラーが頻繁に発生します。中国本土が主なユーザーである場合、Cloudflare Enterprise with China Networkを持っていない限り、このオプションを使用しないでください。
</Warning>

| 変数 | 必須 | デフォルト | 説明 |
|---|---|---|---|
| `CLOUDFLARE_TUNNEL_TOKEN` | **はい**（Tunnelを使用する場合） | — | Cloudflare Zero Trust → Networks → Tunnels → your tunnel → Configureから取得したトークン。`eyJ...`で始まります。`docker-compose.tunnel.yml`の`cloudflared`サイドカーに必要です。 |

## Analytics (Optional)

すべての分析プロバイダーはオプションです。任意の組み合わせを設定できます — すべてのアクティブなプロバイダーが同時に読み込まれます。すべてを空白のままにすると、分析は完全に無効になります（ローカル開発では推奨）。

| Variable | Required | Default | Description |
|---|---|---|---|
| `NEXT_PUBLIC_GA_MEASUREMENT_ID` | No | — | Google Analytics 4 測定 ID（例：`G-XXXXXXXXXX`）。[analytics.google.com](https://analytics.google.com) で取得できます |
| `NEXT_PUBLIC_UMAMI_SCRIPT_URL` | No | — | Umami 分析スクリプト URL（例：`https://your-umami.com/script.js`）。自己ホスト型のプライバシーフレンドリーな代替案 — [umami.is](https://umami.is) |
| `NEXT_PUBLIC_UMAMI_WEBSITE_ID` | No | — | Umami ウェブサイト ID。`NEXT_PUBLIC_UMAMI_SCRIPT_URL` が設定されている場合は必須 |
| `NEXT_PUBLIC_PLAUSIBLE_DOMAIN` | No | — | Plausible 分析ドメイン（例：`yourdomain.com`）。軽量でプライバシーフレンドリー — [plausible.io](https://plausible.io) |
| `NEXT_PUBLIC_PLAUSIBLE_SCRIPT_URL` | No | `https://plausible.io/js/script.js` | 自己ホスト型インスタンス用のカスタム Plausible スクリプト URL |

> すべての `NEXT_PUBLIC_*` 分析変数は**ビルド時**です — 変更を反映させるにはフロントエンドの再ビルドが必要です。

## Stripe Billing (Optional)

Stripe powers paid subscriptions. Leave all three variables blank to disable billing — the rest of FIM One works unchanged. **Both** `STRIPE_SECRET_KEY` **and** `STRIPE_WEBHOOK_SECRET` must be set together; partial config raises an error at first use. Which access posture applies (no subscriptions, included + paid, or paid only) is chosen in the admin panel; see [Billing](/configuration/billing).

| Variable | Required | Default | Description |
|---|---|---|---|
| `STRIPE_SECRET_KEY` | No | — | Stripe API secret key. Must start with `sk_test_` / `sk_live_` (full access) or `rk_test_` / `rk_live_` (restricted key). Get yours from the Stripe Dashboard → Developers → API keys. Never commit a `sk_live_*` key to source. |
| `STRIPE_WEBHOOK_SECRET` | No | — | Stripe webhook signing secret (`whsec_*`). Created when you register the webhook endpoint in Stripe Dashboard → Developers → Webhooks → Add endpoint. Required to verify inbound webhook payloads. |
| `STRIPE_BILLING_RETURN_URL` | No | `http://localhost:3000/settings?tab=billing` | URL Stripe redirects users to after Checkout / Customer Portal sessions. Set this to your production billing settings page (e.g. `https://your-domain.com/settings?tab=billing`). |
