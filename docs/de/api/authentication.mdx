## Übersicht

Die FIM One API unterstützt zwei Authentifizierungsmethoden:

1. **API-Schlüssel** — Einfache, langlebige Token für Service-to-Service-Integration
2. **JWT-Token** — Kurzlebige Token aus Benutzeranmeldung (für SSE-Endpunkte)

Die meisten Integrationen sollten **API-Schlüssel** verwenden.

## API-Schlüssel

API-Schlüssel sind langlebige Anmeldedaten, die an Ihr Benutzerkonto gebunden sind. Sie sind ideal für:

- Server-zu-Server-Integrationen
- Geplante Skripte und Automatisierung
- Externe Anwendungen, die auf FIM One zugreifen

### API-Schlüssel erstellen

1. Melden Sie sich bei Ihrem FIM One-Portal an
2. Gehen Sie zu **Einstellungen → API-Schlüssel**
3. Klicken Sie auf **API-Schlüssel erstellen**
4. Geben Sie einen Namen ein (z. B. „Production Integration")
5. (Optional) Legen Sie Bereiche fest, um den Zugriff einzuschränken
6. (Optional) Legen Sie ein Ablaufdatum fest
7. Klicken Sie auf **Erstellen**
8. Kopieren Sie den Schlüssel sofort – er wird nur einmal angezeigt

Der vollständige Schlüssel sieht wie folgt aus: `fim_your44characterkeystringhere` (beginnt mit dem Präfix `fim_`)

### API-Schlüssel verwenden

Fügen Sie den Schlüssel im `Authorization`-Header als Bearer-Token ein:

```bash
curl -H "Authorization: Bearer fim_your_api_key_here" \
  https://your-domain.com/api/conversations
```

Oder in Python:

```python
import requests

headers = {
    "Authorization": "Bearer fim_your_api_key_here"
}

response = requests.get(
    "https://your-domain.com/api/conversations",
    headers=headers
)
print(response.json())
```

### API-Schlüssel-Funktionen

**Sichtbarkeit**: Jeder Schlüssel zeigt:
- Schlüsselpräfix (erste 8 Zeichen zur Identifikation)
- Erstellungsdatum
- Zeitstempel der letzten Verwendung
- Gesamtanzahl der Anfragen
- Aktivitätsstatus
- Ablaufdatum (falls festgelegt)

**Verwaltung**: Sie können:
- Schlüssel aktivieren/deaktivieren, ohne sie zu löschen
- Automatische Ablaufdaten festlegen
- Schlüssel dauerhaft löschen
- Nutzungsmuster verfolgen

### Scopes

Scopes beschränken, worauf ein API-Schlüssel zugreifen kann. Wenn keine Scopes festgelegt sind, hat der Schlüssel vollständigen Zugriff.

Ein Schlüssel mit Scopes kann nur die Endpunkte aufrufen, die seine Scopes erlauben. Alle anderen Endpunkte antworten mit `403`, einschließlich der API-Schlüsselverwaltung unter `/api/me/api-keys`, die einen Schlüssel ohne Scopes oder eine angemeldete Sitzung benötigt. Ein Schlüssel kann niemals einen Schlüssel mit umfassenderen Scopes als seinen eigenen erstellen.

Verfügbare Scopes:

| Scope | Erlaubt |
|-------|--------|
| `chat` | POST /api/react, POST /api/dag, POST /api/auto, POST /api/chat/ticket, POST /api/chat/inject, POST /api/chat/inject/recall, POST /api/chat/resume, und GET/POST /api/conversations, GET/PATCH/DELETE /api/conversations/`{id}` |
| `agents` | GET /api/agents, GET /api/agents/`{id}` |
| `kb` | GET /api/knowledge-bases, POST /api/knowledge-bases/`{id}`/retrieve |
| `connectors` | Alles unter /api/connectors |
| `admin` | Alles unter /api/admin (der Eigentümer des Schlüssels muss ein Administrator sein) |

Erstellen Sie einen Schlüssel mit Scopes:

```bash
curl -X POST https://your-domain.com/api/me/api-keys \
  -H "Authorization: Bearer your_current_api_key_or_jwt" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Chat-only Integration",
    "scopes": "chat"
  }'
```

## JWT Tokens

JWT tokens are short-lived and issued at login. They're used for:

- **SSE Streaming Endpoints**: Pass tokens in the request body for `/api/react`, `/api/dag` and `/api/auto`
- **Portal Session**: Frontend authentication

### JWT-Token abrufen

JWT-Token werden automatisch ausgestellt, wenn Sie sich über das Web-Portal anmelden oder den Authentifizierungsendpunkt aufrufen:

```bash
curl -X POST https://your-domain.com/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{
    "email": "user@example.com",
    "password": "your_password"
  }'
```

Antwort:

```json
{
  "access_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
  "refresh_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
  "token_type": "bearer",
  "expires_in": 7200,
  "user": { ... }
}
```

### Two-factor authentication

When the account has two-factor authentication enabled, sign-in does not return tokens. `POST /api/auth/login` and `POST /api/auth/login-with-code` answer with a short-lived temporary token instead:

```json
{
  "requires_2fa": true,
  "temp_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9..."
}
```

Send it with the TOTP code (or a backup code) to finish signing in. The response is the same token payload as a normal login:

```bash
curl -X POST https://your-domain.com/api/auth/login/verify-2fa \
  -H "Content-Type: application/json" \
  -d '{
    "temp_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
    "code": "123456"
  }'
```

The temporary token is valid for 5 minutes. Signing in through an OAuth provider (GitHub, Google, Discord, Feishu) stops at the same step: the callback hands the browser a 2FA challenge instead of tokens. After 5 incorrect codes within 15 minutes for the same account, the endpoint answers `429` with `error_code` `2fa_too_many_attempts`; starting a new sign-in does not reset the count.

### Using JWT for Streaming

For SSE endpoints, include the token in the request body. The field accepts a JWT access token or an API key (a scoped key needs the `chat` scope):

```bash
curl -X POST https://your-domain.com/api/react \
  -H "Content-Type: application/json" \
  -d '{
    "q": "What are the top 3 Python frameworks?",
    "token": "your_jwt_token_here"
  }'
```

Or from JavaScript using `fetch` with a readable stream (the endpoint is POST-only, so native `EventSource` which only supports GET cannot be used):

```javascript
const response = await fetch("https://your-domain.com/api/react", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({
    q: "Hello",
    token: "fim_your_api_key_here"
  })
});

const reader = response.body.getReader();
const decoder = new TextDecoder();

while (true) {
  const { done, value } = await reader.read();
  if (done) break;
  const chunk = decoder.decode(value);
  // Parse SSE events from chunk
  console.log(chunk);
}
```

### Token-Aktualisierung

Zugriffstoken verfallen nach 2 Stunden. Verwenden Sie das Aktualisierungstoken, um ein neues Zugriffstoken zu erhalten, ohne sich erneut anzumelden:

```bash
curl -X POST https://your-domain.com/api/auth/refresh \
  -H "Content-Type: application/json" \
  -d '{
    "refresh_token": "your_refresh_token_here"
  }'
```

## Sicherheitsbest Practices

### API-Schlüssel

<Warning>
**Committen Sie API-Schlüssel niemals in die Versionskontrolle.** Sie bieten vollständigen Zugriff auf Ihre Daten.
</Warning>

1. **Speichern Sie in Umgebungsvariablen**:
   ```bash
   export FIM_API_KEY="fim_your_api_key_here"
   ```
   Dann referenzieren Sie im Code:
   ```python
   api_key = os.environ.get("FIM_API_KEY")
   ```

2. **Verwenden Sie Schlüsselrotation**:
   - Erstellen Sie einen neuen Schlüssel
   - Aktualisieren Sie Ihre Anwendung
   - Löschen Sie den alten Schlüssel
   - Wiederholen Sie dies vierteljährlich

3. **Legen Sie Ablaufdaten fest**:
   - Verwenden Sie kurzlebige Schlüssel für temporäre Integrationen
   - Erfordern Sie regelmäßige Wiederauthentifizierung

4. **Verwenden Sie begrenzte Schlüssel**:
   - Verwenden Sie keine Schlüssel mit „vollständigem Zugriff", wenn nicht notwendig
   - Erstellen Sie separate Schlüssel für verschiedene Dienste
   - Begrenzt Schäden, wenn ein Schlüssel kompromittiert wird

5. **Überwachen Sie die Nutzung**:
   - Überprüfen Sie die Zeitstempel „zuletzt verwendet"
   - Überprüfen Sie Anfragezählungen
   - Löschen Sie ungenutzte Schlüssel

### JWT Tokens

1. **Kurze Gültigkeitsdauer beibehalten**: Zugriffstokens verfallen nach 2 Stunden
2. **Sichere Speicherung**:
   - In Browsern: HttpOnly-Cookies verwenden (sicherer als localStorage)
   - Auf Servern: sichere Sitzungsspeicherung verwenden
3. **Niemals in Protokollen offenlegen**: Nur das Token-Präfix protokollieren, nicht das vollständige Token
4. **Nur HTTPS verwenden**: Tokens niemals über unverschlüsselte Verbindungen senden

## Ratenlimits

Pro-Schlüssel-Ratenlimits sind für eine zukünftige Version geplant. Derzeit gibt es keine durchgesetzten Pro-Schlüssel-Anfragenlimits.

## Troubleshooting

Every error response has the shape `{"detail", "error_code", "error_args"}`. Errors raised while checking the `Authorization` header carry `error_code: null`; tell them apart by the status code and `detail`.

### Invalid Token Error

```json
{
  "detail": "Invalid token",
  "error_code": null,
  "error_args": {}
}
```

**Causes** (`401`; `detail` is `Invalid token`, `Invalid API key`, `API key is disabled` or `API key has expired`):
- API key prefix is wrong (must start with `fim_`)
- Token is malformed or corrupted
- API key has been deleted, disabled, or is past its expiration date

**Solution**: Verify your token format and re-generate if necessary

### Unauthorized Error

```json
{
  "detail": "Authentication required",
  "error_code": "authentication_required",
  "error_args": {}
}
```

**Causes** (`401`):
- Token is missing from the request body (SSE endpoints return the body above)
- No `Authorization` header provided (other endpoints answer `Not authenticated` with `error_code: null`)

**Solution**: Include a valid token in every request

### Forbidden Error

```json
{
  "detail": "This API key's scopes do not allow this request",
  "error_code": "api_key_scope_denied",
  "error_args": {}
}
```

**Causes** (`403`):
- API key has scoped access and lacks the required scope (`api_key_scope_denied`)
- The client address is refused by the instance's IP rules (`ip_not_allowed`, see below)
- The account is disabled (`detail`: `Account disabled`) or lacks the role the endpoint needs

**Solution**: Use a key with the appropriate scope or increase key privileges

### IP Rules

Administrators can restrict API access by client address under admin **Security → IP Rules**. A request from an address that matches a deny rule, or that matches no allow rule when allow rules exist, is refused before authentication:

```json
{
  "detail": "Access from this IP address is not allowed.",
  "error_code": "ip_not_allowed",
  "error_args": {}
}
```

`/api/version`, `/api/webhooks/` and CORS preflight requests are exempt. Behind a reverse proxy the instance must be told which proxy to trust (`FORWARDED_ALLOW_IPS`), otherwise every request appears to come from the proxy; see [Environment Variables](/configuration/environment-variables#platform).

### Expired Token

```json
{
  "detail": "Token has expired",
  "error_code": null,
  "error_args": {}
}
```

On the SSE endpoints, which read the token from the request body, the same condition returns `error_code` `token_expired`.

**Solution**: Use the refresh token to get a new access token:

```bash
curl -X POST https://your-domain.com/api/auth/refresh \
  -H "Content-Type: application/json" \
  -d '{"refresh_token": "your_refresh_token"}'
```

## Umgebungsvariablen-Einrichtung

### Python

```python
import os
from dotenv import load_dotenv
import requests

# Load from .env file
load_dotenv()

api_key = os.getenv("FIM_API_KEY")
base_url = os.getenv("FIM_API_BASE_URL", "https://your-domain.com/api")

headers = {"Authorization": f"Bearer {api_key}"}

# Now use in requests
response = requests.get(f"{base_url}/agents", headers=headers)
```

### Node.js

```javascript
const api_key = process.env.FIM_API_KEY;
const base_url = process.env.FIM_API_BASE_URL || "https://your-domain.com/api";

const headers = {
  "Authorization": `Bearer ${api_key}`,
  "Content-Type": "application/json"
};

// Use in fetch
const response = await fetch(`${base_url}/agents`, {
  headers: headers
});
```

### Bash

```bash
#!/bin/bash

FIM_API_KEY="${FIM_API_KEY:-$(cat ~/.fim_api_key)}"
FIM_API_BASE_URL="${FIM_API_BASE_URL:-https://your-domain.com/api}"

curl -H "Authorization: Bearer $FIM_API_KEY" \
  "$FIM_API_BASE_URL/agents"
```

- Check that a token is still accepted with `GET /api/auth/me`
- Contact support if you believe a key has been compromised
